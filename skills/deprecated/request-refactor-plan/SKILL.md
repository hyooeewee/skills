  或将重构分解为安全增量步骤时使用。

---

当用户想要创建重构请求时，将调用此技能。你应该遵循以下步骤。如果不认为有必要，可以跳过某些步骤。

1. 询问用户关于他们想要解决的问题的详细描述，以及任何潜在的解决方案想法。

2. 探索仓库以验证他们的断言并理解代码库的当前状态。

3. 询问他们是否考虑过其他选项，并向他们展示其他选项。

4. 就实现方案对用户进行访谈。要极其详细和全面。

5. 确定实现的精确范围。弄清楚你计划改变什么以及计划不改变什么。

6. 检查代码库中此区域的测试覆盖率。如果测试覆盖率不足，询问用户他们的测试计划是什么。

7. 将实现分解为一系列微小提交的计划。记住 Martin Fowler 的建议：“尽可能让每一步重构都尽可能小，这样你总能看到程序在运行。”

8. 使用重构计划创建一个 GitHub Issue。使用以下模板作为问题描述：

<refactor-plan-template>

## 问题陈述

开发者面临的问题，从开发者的角度来看。

## 解决方案

问题的解决方案，从开发者的角度来看。

## 提交

一份详细的实施计划。用通俗英语编写计划，将实施分解为尽可能小的提交。每个提交都应该使代码库处于可工作状态。

## 决策文档

做出的实施决策列表。这可能包括：

* 将要构建/修改的模块
* 将要修改的这些模块的接口
* 来自开发者的技术澄清
* 架构决策
* 模式变更
* API 协议
* 特定的交互

不要包含具体的文件路径或代码片段。它们可能会很快过时。

## 测试决策

做出的测试决策列表。包括：

* 什么构成了好的测试的描述（仅测试外部行为，不测试实现细节）
* 将测试哪些模块
* 测试的先例（即代码库中类似类型的测试）

## 超出范围

关于此重构超出范围的事物的描述。

## 进一步说明（可选）

关于重构的任何进一步说明。

</refactor-plan-template>
