你收到了一个规范。该规范应该有关联的任务，用来描述如何实现该规范。

问题追踪器应该已经提供给你了。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。

目标是在单个 **集成分支** 上实现整个规范，每个任务都按照问题追踪器关闭工作的方式解决。

任务不是步骤列表。它们是一个具有阻塞关系的**任务图**。这意味着总有一组（**前沿**）任务准备好被获取。

与子代理之间的通信应保持简练。主要通过**上下文指针**进行沟通：指向规范、任务、研究笔记和以前的提交。不要复制通过指针已经获取的信息。

**实现者子代理** 应尽可能在后台运行以实现最大并发。

## 步骤

1. 阅读规范和任务以理解任务图。

2. （可选）使用**探索子代理**执行任务所需的任何探索——相关的代码库文件或外部文档。确保探索子代理可以保存文件——它应该将其 markdown 笔记保存在仓库外的目录中，供所有未来的子代理访问。这样可以让**实现者子代理**专注于实现，而不是探索。

3. 创建集成分支。如果问题追踪器通过 PR 关闭工作，或者用户要求，请在第 5 步第一次合并后打开一个草稿 PR（没有领先 main 分支提交的分支无法打开 PR），标记为关闭规范和任务。

4. 使用 **实现者子代理** 实现每个任务，每个任务在自己的工作树和自己的分支上。每个实现者子代理：
   * 确认其工作树基于集成分支后再开始，如果不是则重置到该分支；
   * 使用 `tdd` 调用 Skill 工具来构建任务；
   * 在报告完成前将集成分支的最新提交合并到自己的分支中

5. 一旦 **实现者子代理** 完成，使用 **合并子代理** 将其工作合并到集成分支。

6. 如果这改变了可用任务的**前沿**，则启动更多**实现者子代理**来处理新任务。这允许实现最大并发。

7. 所有任务完成后，在集成分支上使用 `code-review` 调用 Skill 工具。在单个 **实现者子代理** 中修复代码审查提出的所有问题。

8. 如果存在草稿 PR，将其标记为准备好供审查。否则，按照问题追踪器关闭工作的方式解决每个任务，并报告集成分支。

9. 清理所有**实现者子代理**的工作树。
