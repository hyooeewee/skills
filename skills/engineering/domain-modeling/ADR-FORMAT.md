# ADR 格式

ADR 存放在 `docs/adr/` 目录中，并使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

懒加载创建 `docs/adr/` 目录：仅当需要第一个 ADR 时才创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一个 ADR 可以是一段话。价值在于记录*做出了*一个决定以及*原因*，而不是去填充各个部分。

## 可选部分

仅当这些部分能带来真正的价值时才包含它们。大多数 ADR 并不需要。

* **Status** 元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当重新审视决策时很有用。
* **Considered Options**（考虑的选项）：仅当被拒绝的替代方案值得记住时。
* **Consequences**（后果）：仅当需要指出不明显的影响时。

## 编号

扫描 `docs/adr/` 找到现有的最大编号并加一。

## 何时提出 ADR

以下三个条件必须同时成立：

1. “难以回撤”：日后改变主意成本很高。
2. **Surprising without context**（缺乏上下文会令人惊讶）：未来的读者在查看代码时会纳闷“他们到底为什么要这么做？”
3. “真实权衡的结果”：存在真正的替代方案，而你出于特定原因选择了其中一个。

如果一个决定容易回撤，就跳过它：你只会把它回撤。如果它并不令人惊讶，没人会想知道为什么。如果没有真正的替代方案，除了“我们做了显而易见的事”之外，就没有什么可记录的了。

### 哪些决策符合条件

* **架构形态。** “我们正在使用 monorepo。” “写模型是事件溯源的，读模型投影到 Postgres 中。”
* **上下文之间的集成模式。** “订单和计费通过领域事件进行通信，而不是同步 HTTP。”
* **Technology choices that carry lock-in**（具有锁定效应的技术选择）。数据库、消息总线、认证提供方、部署目标。不是每个库：只是那些需要花费一个季度才能替换掉的库。
* **边界和范围决策。** “客户数据归客户上下文所有；其他上下文仅通过 ID 引用它。” 明确的“不”和“是”同样有价值。
* **刻意偏离显而易见的方式。** “我们因为 X 而使用手写 SQL 而不是 ORM。” 任何理性的读者都会假设相反的情况。这些记录可以阻止下一位工程师“修复”那些刻意为之的东西。
* **代码中不可见的约束。** “由于合规要求，我们不能使用 AWS。” “由于合作伙伴 API 合同，响应时间必须低于 200 毫秒。”
* **Rejected alternatives when the rejection is non-obvious**（当拒绝并不明显时的被拒绝替代方案）。如果你考虑了 GraphQL 并因为微妙的原因选择了 REST，就把它记录下来；否则六个月后有人会再次建议使用 GraphQL。
