# 分类处理

将项目问题跟踪器上的问题通过分类处理角色的状态机进行流转。

如果此仓库将外部拉取请求视为请求入口（请参阅问题跟踪器配置），分类处理也会涵盖它们：**一个 PR 是带有附加代码的问题** — 相同的角色、相同的状态、相同的机器，下面有几个标记为“针对 PR”的差异。根据跟踪器配置将裸 `#42` 解析为问题或 PR。

在分类处理期间发布到问题跟踪器的每条评论或问题**必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

* [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写持久的代理简报
* [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库的工作原理

## 角色

两个**类别**角色：

* `bug` — 某处损坏
* `enhancement` — 新功能或改进

五个**状态**角色：

* `needs-triage` — 维护者需要评估
* `needs-info` — 等待报告人提供更多信息
* `ready-for-agent` — 已完全指定，准备好供离线代理使用
* `ready-for-human` — 需要人工实现
* `wontfix` — 将不会采取行动

对于 PR，相同的状态是针对附加代码读取的：`ready-for-agent` 意味着已附加简报，代理应该在差异上采取下一步行动；`ready-for-human` 意味着它准备好供人工合并。

每个经过分类处理的问题应该恰好携带一个类别角色和一个状态角色。如果状态角色冲突，将其标记出来，并在做其他任何事情之前询问维护者。

这些是规范的角色名称 — 问题跟踪器中使用的实际标签字符串可能不同。映射应该已经提供给您了 — 如果没有，运行 `/setup-matt-pocock-skills`。

状态转换：未标记的问题通常首先进入 `needs-triage`；从那里它移动到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告人回复，`needs-info` 返回到 `needs-triage`。维护者可以随时覆盖 — 标记看起来不寻常的转换并在继续之前询问。

## 调用

维护者调用 `/triage` 命令并用自然语言描述他们的需求。解释请求并执行操作。示例：

* "Show me anything that needs my attention"
* "Let's look at #42"（问题或 PR）
* "Move #42 to ready-for-agent"
* "What's ready for agents to pick up?"

## 显示需要注意的事项

查询问题跟踪器并展示三个桶，按时间从旧到新排序：

1. **未标记** — 从未经过分类处理。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且自上次分类处理笔记以来有报告人活动** — 需要重新评估。

当 PR 在范围内时，在这些桶中包含外部 PR，并标记每行 `[PR]` 或 `[issue]`。发现仅显示 *外部* PR（跟踪器配置定义了谁算作外部）——协作者的进行中的 PR 不是分类处理工作。此过滤器仅用于发现；显式命名的 PR 总是会被分类处理，无论作者是谁。

显示每个项目的计数和一行摘要。让维护者选择。

## 分类处理特定问题或 PR

1. 收集上下文。阅读完整的问题或 PR（正文、评论、标签、作者、日期；对于 PR，还有差异）。解析任何先前的分类处理笔记，以免重复询问已解决的问题。使用项目的领域词汇表探索代码库，并尊重该区域的 ADR。对代码库运行两次检查：(a) **冗余** — 通过领域概念（不仅仅是请求的措辞）搜索所请求行为的现有实现，并报告您查看的位置。如果找到，它是一个已经实现的 `wontfix`（第 5 步）。(b) **先前拒绝** — 阅读 `.out-of-scope/*.md` 并找出任何类似于此请求的内容。

2. 推荐。告诉维护者您的类别和状态推荐以及理由，加上与请求相关的简要代码库摘要——包括是否已实现。等待指示。

3. 验证主张。在质询之前，检查主张是否成立。对于 bug，从报告人的步骤中重现它。对于 PR，确认差异确实按其声称的那样工作 — 检出它，运行相关的测试或命令。报告发生了什么：已确认（带有代码路径），失败，或细节不足（强烈的 `needs-info` 信号）。确认的验证会使代理简报强得多。

4. 质询（如果需要）。如果请求需要充实内容，请同时运行 `/grilling` 和 `/domain-modeling` 技能——通过一轮轮问题将其理顺，精炼领域术语，并在决策落地时内联更新 `CONTEXT.md`/ADRs。

5. **应用结果：**
   * `ready-for-agent` — 发布代理简报评论 ([AGENT-BRIEF.md](AGENT-BRIEF.md))。
   * `ready-for-human` — 结构与代理简报相同，但注明为什么不能委托（判断、外部访问、设计决策、手动测试）。
   * `needs-info` — 发布分类处理笔记（下方有模板）。
   * `wontfix` — 关闭，评论取决于*为什么*：
     * **已实现** — 更改已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（该 KB 是用于 *被拒绝* 的请求，而不是已构建的请求）。
     * **被拒绝 (bug)** — 礼貌的解释，然后关闭。
     * **被拒绝 (增强功能)** — 写入 `.out-of-scope/`，从评论中链接到它，然后关闭 ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))。
   * `needs-triage` — 应用角色。如果有部分进度，则添加可选评论。

## 快速状态覆盖

如果维护者说“将 #42 移动到 ready-for-agent”，相信他们并直接应用角色。确认您将要做什么（角色更改、评论、关闭），然后行动。跳过质询。如果在不进行质询会话的情况下移动到 `ready-for-agent`，询问他们是否想要编写代理简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

在“已确立内容”下捕获质询期间解决的所有内容，以免工作丢失。问题必须具体且可操作，而不是“请提供更多信息”。

## 恢复之前的会话

如果问题或 PR 上存在先前的分类处理笔记，请阅读它们，检查报告人是否回答了任何悬而未决的问题，并在继续之前呈现更新后的情况。不要重新询问已解决的问题。
