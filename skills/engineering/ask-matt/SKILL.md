# 向 Matt 提问

你不会记得每一个技能，所以问吧。

在说明某个技能的作用或建议跳过某个步骤之前，请先阅读该技能的 SKILL.md：此处的摘要仅供定向参考。

**流程（flow）** 是贯穿各技能的一条路径。大多数路径沿一条**主流程（main flow）** 行进，并有两条**入口匝道（on-ramps）** 汇入其中。其余一切都是独立的，或者是一个在其底下运行的词汇层。

## 主流程：想法 → 交付

大多数工作所走的路线。你有一个想法，并希望把它构建出来。

1. **`/grill-with-docs`** 通过访谈来锐化想法。每当你**在工作目录中工作**时，请从这里开始：它是有状态的，会将所学内容保留在 `GLOSSARY.md` 和 ADRs 中。（没有工作目录？请改用 `/grill-me`，见独立技能。两者运行相同的 `/grilling` 原语；`grill-with-docs` 会留下书面记录，因此只要有仓库可供记录，它就是两者中更好的选择。）

2. 分支：你能否在对话中解决每个问题？如果一个问题需要可运行的答案（状态、业务逻辑、你必须看到的 UI），请绕过原型，通过 **`/handoff`** 双向桥接（原型存在于自己的目录中，这正是 `/handoff` 的用途；参见阶段边界）：
   * **`/handoff`** 出去，然后针对该文件打开一个新会话，
   * **`/prototype`** 用一次性代码来回答这个问题，
   * **`/handoff`** 带回你学到的东西，并从原始想法线程中引用它。

3. **Branch: is this a multi-session build?**

   * **是** → **`/to-spec`** （将线程转化为规格），然后 **`/to-tickets`** 将其拆分为示踪票据，每个票据声明其**阻塞边**。随后通过以下两种方式之一处理票据：
     * **`/implement`** 逐个票据执行，每个票据之间 **`/clear` 清理上下文**。在本地追踪器上，这是 `.scratch/<feature>/issues/` 下每个票据对应一个文件，手动按阻塞优先顺序处理；在真正的追踪器上，边会变成原生阻塞链接，因此所有阻塞项完成的票据即可领取。每个票据自包含，因此最后一个票据的上下文可丢弃。
     * **`/implement-spec`** 一次性完成整个规格。它将票据读取为**任务图**，跨就绪**前沿**并行运行实现子代理，并将所有内容落地到同一**集成分支**。当你更倾向于编排构建而非亲自驱动每个票据时，请使用它。
   * **否** → 就在同一个上下文窗口中调用 **`/implement`**。

   无论哪种方式，代码都通过驱动 **`/tdd`**（一次一个红-绿切片）来构建，并以 **`/code-review`** 收尾，对差异进行双轴审查（标准 + 规格）。`/implement` 对每个票据运行两者；`/implement-spec` 的实现者各自驱动 `/tdd`，并在集成分支上运行一次 `/code-review`。当你只想在没有完整规格的情况下以测试优先方式构建具体行为时，单独使用 **`/tdd`**；当你想针对固定基准审查分支或 PR 时，单独使用 **`/code-review`**。

   当工作作为拉取请求提交时， **`/pr`** 会生成正文：展示变更的最小可视化内容、前后对比的工作证据，以及单向或双向门决策。它是模型调用的，因此智能体在撰写 PR 时会自动使用它。

4. **`/retro`** 闭环。在一次构建后，特别是偏离轨道的构建后，它回顾会话并建议对智能体的**环境**而非代码进行更改：导航指针、自动化检查、 `/code-review` 强制执行的编码标准、指导文件、工具。机械性错误变成确定性检查；判断性决定变成编码标准。下一次构建便从更好的环境起步。

### 上下文卫生

将步骤 1-3 保持在**一个未中断的上下文窗口**中（在 `/to-tickets` 之前不要压缩或清理），以便问答、规格和票据都建立在同一思考之上。随后每个 `/implement` 从票据出发全新开始。在被回顾的会话中运行 `/retro`，在清理之前；清理后，将其指向该会话的日志。

其限制在于\*\*[智能区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)\*\*：模型仍能敏锐推理的窗口（最先进模型上约为 150k 个 token）。如果会话在 `/to-tickets` 之前接近它，不要在降级状态下继续；在最近的阶段边界处 `/compact` 并继续（参见阶段边界）。

## 入口匝道

一种会产生工作的起始情况，然后汇入主流程。

* **Bug 和请求堆积** → **`/triage`**。它让问题经过分诊角色，并产生可供 agent 处理的问题，之后由 **`/implement`** 接手。

  分诊仅针对**你未创建**的问题：错误报告、传入的功能请求、任何原始到达的内容。`/to-tickets` 产生的票据已经是 agent 就绪的，所以**不要对它们进行分诊**。

* **出了故障** → **`/diagnosing-bugs`**。针对棘手的：一眼看不穿的 bug、间歇性抖动、在两个已知良好状态之间悄悄潜入的回归。它拒绝理论化，直到拥有**紧反馈回路**（一个命令已经能在*这个* bug 上变红），再用回归测试修复。修复进入后，在同一会话中运行 **`/retro`** 询问什么本可预防该 bug；若真正发现是没有好的接缝可锁死，那就是 **`/improve-codebase-architecture`** 的工作了。

* 一个巨大的、模糊的努力：一个空白项目或巨大的功能构建，对于一次会话来说太大了 → **`/wayfinder`**，这是这里认知要求最高的流程。当从这里到目的地的路还不可见时，它绘制了问题追踪器上 **决策票据** 的**共享地图**，并逐一解决它们，产生**决策，而不是可交付物**，直到迷雾被推回，道路清晰。**`/grill-with-docs`** 锐化你在一次会话中可以持有的想法的地方，wayfinder 是针对你无法持有的想法，它更慢更密集，所以只为此保存它，绝不是一个范围良好的功能。

  当地图清除时，**它移交，不构建**：汇入主流程在 **`/to-spec`**，它将地图的链接决策折叠成可执行计划，然后像往常一样 `/to-tickets` 和 `/implement`。将地图直接循环到 `/implement` 跳过了这种折叠并丢弃了链接的细节，所以只有当工作量真正很小时，才直接去 `/implement`。

## 代码库健康

不是功能工作，只是维护。

* **`/improve-codebase-architecture`** 在你有空闲时间保持代码库良好以便 agent 操作时运行。它暴露了**加深机会**；选择一个 *生成一个想法*，你可以将其带到主流程在 `/grill-with-docs`。它是发现候选人的调查；**`/codebase-design`**（下面）是你设计所选的那个的工作台。

## 底层词汇层

两个由模型调用的引用，在*下面*运行其他技能，每个都是其词汇的单一事实来源。当**词语**，而不是流程，是问题时，直接使用它们；或者让上面的技能将它们拉入。

* **`/domain-modeling`**：锐化项目的*领域*语言：挑战模糊术语，消解过载词汇（"account" 承担三种职责），将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动的主动规范，用于保持 `GLOSSARY.md` 为一个干净的词汇表。
* **`/codebase-design`** 是用于设计模块*形状*的深层模块词汇（模块、接口、深度、接缝、适配器、杠杆作用、局部性）：在一个干净的接缝处，小接口后有很多行为。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 阶段边界

一个**阶段**是会话内的一块工作：问答、实现、QA。在它们之间的**边界**上，你有五个选项，在它们之间选择是整个地图中最模糊的决定：

* 继续：保持原地。不花费任何东西，不丢失任何东西。
* **`/clear`**：清空窗口，当这里没有什么对接下来重要的。
* **`/handoff`** 写一个可移植的 markdown 文件。狭窄：仅用于**新的工具链**、**新目录**、**同事**，或在**中期阶段**分叉一个侧边任务。它买来的是可移植性。
* 子代理：将一个范围紧密的任务发送到它自己的窗口并获得报告。
* **`/compact`** 压缩此上下文并用它播种一个新会话。**默认**，在树的底部而不是第一次触及。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以获取有序树：五个问题，每个分支背后的推理，以及为什么源成本使 **Continue** 成为首先排除的那个。在**边界**处做出决定；在中期阶段，继续或将剩余部分分成子代理。

## 独立技能

完全脱离主流程。

* **`/grill-me`**：与 `/grill-with-docs` 同样的无情访谈，但**无状态**：不在本地保存任何内容，不生成 `GLOSSARY.md`。当你**不在工作目录中工作**时（锐化计划、设计、一篇文章，任何没有底层仓库的场景）请使用它。如果你在工作目录中，请改用 `/grill-with-docs`：它运行相同的访谈并留下书面记录，因此严格更优。
* 是面试的原语本身：轮次、前沿、事实是智能体的工作，而决策是你的。`/grill-me` 和 `/grill-with-docs` 是两个命名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有在不需要任何包装器的情况下，才直接使用它。
* 是一个小型的一次性程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。“一次性”是对代码编写方式的约束，而不是销毁它的承诺：答案会融入真实代码中，原型本身会作为**主要来源**保留在从 main 分支出来的 `prototype/<name>` 分支上，并由实施问题指向它。它是主流程第 2 步的绕路，但在设计问题很难在纸上确定时，随时可以使用它。
* 将阅读的基础工作委托给一个**后台智能体**：它根据**主要来源**调查一个问题，然后在仓库中留下一个引用的 Markdown 文件。在它阅读时继续工作。它生成的文件是带到 `/grill-with-docs` 的主流程中的东西，因为研究填充了思考，而不是取代了思考。
* 当阻碍你的东西不在你的脑海或代码库中，而是在**他人**手中时，它会出现，并为他们写一份要填写的问卷。它是 `/grill-me` 的反义词：它不采访你关于主题的内容，而是采访你关于**发送**（发给谁，你需要什么回来），并将问题指向差距。返回的内容是 `/grill-with-docs` 或 `/to-spec` 的材料。
* 是只有**人类**才能执行的步骤：配置基础设施、设置凭证或 CI 密钥、点击不熟悉的三方仪表板、运行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL，捕获每个值，并将其写入 `.env` 和 GitHub 密钥，这样该程序就不会每次都变成你需要重新向智能体解释的东西。由模型调用，因此智能体一旦遇到只有你能通过的障碍，就会使用它。如果智能体自己就能做，它应该这样做；这是针对人类真正参与其中的情况。
* **`/wait-what`** 是针对未着陆信息的纠偏。在对话中途、任何其他技能内部使用它，智能体会用你缺失的上下文、用通俗英语、用 `GLOSSARY.md` 的词汇，重新讲述它刚才说的内容。它事后生效；`/grill-with-docs` 是事前的治本之道，因为尽早达成的共享语言才能彻底阻止行话的入侵。
* 通过多个会话学习一个概念，使用当前目录作为有状态的工作区。
* 是编写智能体消费的文档的参考：技能、AGENTS.md、指向的文档。

## 前置条件

在第一次工程流程之前运行，以配置其他技能所假设的问题跟踪器、分类标签和文档布局。自定义问题跟踪器也有效。
