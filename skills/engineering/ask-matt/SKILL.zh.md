# 询问 Matt

您不可能记住每个技能，所以请提问。

**流程**是技能路径。大多数路径沿着一条**主流程**运行，两条**入口**汇入其中。其余的都是独立的，或底层运行的词汇层。

## 主流程：想法 → 发布

大多数工作走的路线。您有一个想法并希望它被构建。

1. 通过面试打磨想法。每当您**在开发目录中工作时**，从这里开始：它是有状态的，保留其在 `CONTEXT.md` 和 ADR 中学到的东西。（没有工作目录？使用 `/grill-me` —— 见 Standalone。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留下书面记录的那个，所以只要仓库在那里可以留下记录，它就是两者中更好的一个。）
2. 分支 —— 您能否在对话中解决每个问题？如果一个问题需要可运行的答案（状态、业务逻辑、必须看到的 UI），则绕过原型，通过 **`/handoff`** 在两个方向上桥接（原型驻留在自己的目录中，这正是 `/handoff` 的用途 —— 见 Phase boundaries）：
   * **`/handoff`** 转出，然后打开一个新会话来处理该文件，
   * **`/prototype`** 用一次性代码回答问题，
   * **`/handoff`** 转回您学到的东西，并从原始想法线程中引用它。
3. **分支 —— 这是一个多会话构建吗？**

   * 是 → **`/to-spec`**（将线程转换为规范），然后 **`/to-tickets`** 将其拆分为追踪子弹工单，每个工单声明其**阻塞边**。在本地跟踪器上，每个工单是一个文件位于 `.scratch/<feature>/issues/` 下，手动优先处理阻塞项；在真实跟踪器上，边变成原生的阻塞链接，因此任何阻塞项已完成的工单都可以被获取 —— 为每个工单启动 **`/implement`**，**在每一个之间清除上下文**。每个工单都是自包含的，所以最后一个工单的上下文是可以丢弃的。
   * 否 → 在同一个上下文窗口中直接 **`/implement`**。

   无论哪种方式，**`/implement`** 都通过在内部驱动 **`/tdd`** 来构建每个问题 —— 一次一个红绿切片 —— 然后通过运行 **`/code-review`** 结束，这是对差异的双轴审查（标准 + 规范），然后提交。当您只想构建具体的行为测试（无需完整规范）时使用 **`/tdd`**，当您想针对固定点审查分支或 PR 时使用 **`/code-review`**。

### 上下文卫生

将步骤 1–3 保持在**一个不间断的上下文窗口**中 —— 在 **`/to-tickets`** 之后才压缩或清除 —— 这样面试、规范和工单都建立在相同的思考之上。每个 **`/implement`** 然后从工单开始，重新开始。

这的限制是 **[智能区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能清晰推理的窗口（最先进模型上约为 150k tokens）。如果会话在 `/to-tickets` 之前接近它，不要在降级状态下继续 —— 在最近的阶段边界处 `/compact` 并继续（见 Phase boundaries）。

## 入口

产生工作然后汇入主流程的起始情况。

* **Bug 和请求堆积** → **`/triage`**。它将问题通过分类角色，产生可供代理使用的问题，稍后由 **`/implement`** 拾取。

  分类仅适用于您**没有创建**的问题 —— Bug 报告、传入的功能请求、任何原始到达的内容。由 **`/to-tickets`** 产生的问题是已经可供代理使用的，所以**不要对它们进行分类**。

* **某些东西坏了** → **`/diagnosing-bugs`**。对于棘手的问题：那些第一眼就抗拒的 Bug，间歇性的故障，在两个已知良好状态之间潜入的回归。它拒绝假设，直到它有一个**紧密的反馈循环** —— 一个已经在*这个* Bug 上变红的命令 —— 然后用回归测试修复它。当真正的发现是没有好的接缝来锁定 Bug 时，其事后分析会移交给 **`/improve-codebase-architecture`**。

* **巨大的、模糊的努力** —— 绿地项目或巨大的功能构建，对于单个会话来说太大了 → **`/wayfinder`**，这里认知要求最高的流程。当从这里到目的地的路径还不清楚时，它在问题跟踪器上绘制**决策工单**的**共享地图**，并逐个解决它们 —— 产生**决策**，而不是**交付物** —— 直到雾气被推回，路径清晰。当 **`/grill-with-docs`** 打磨您可以在一个会话中掌握的想法时，wayfinder 是用于您无法掌握的想法 —— 它更慢更密集，所以只把它留给那个，永远不要留给一个范围良好的功能。

  当地图清除时，**它移交，不构建**：在 **`/to-spec`** 处汇入主流程，这将地图的链接决策折叠成可构建的计划，然后是 **`/to-tickets`** 和 **`/implement`**。将地图直接循环到 **`/implement`** 会跳过折叠并丢弃链接的细节 —— 只有当工作量确实很小时才直接去 **`/implement`**。

## 代码库健康

不是功能工作 —— 维护。

* **`/improve-codebase-architecture`** — 当您有片刻空闲时间来保持代码库良好以便代理在其中操作时运行。它揭示**深化机会**；选择一个会生成一个想法，您可以将其带入主流程中的 **`/grill-with-docs`**。它是找到候选者的调查；**`/codebase-design`**（下方）是您设计所选内容的平台。

## 底层词汇

两个由模型调用的引用，在*其他技能之下*运行 —— 每个都是其词汇的单一事实来源。当**词语**而不是过程是问题时，直接使用它们；或者让上面的技能将它们拉入。

* **`/domain-modeling`** — 打磨项目的*领域*语言：挑战模糊术语，解决过载的单词（“账户”做三份工作），将难以逆转的决策记录为 ADR。它是 **`/grill-with-docs`** 驱动的主动学科，以保持 `CONTEXT.md` 成为干净的词汇表。
* **`/codebase-design`** — 深度模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用于设计模块的*形状*：在干净的接缝处，小接口背后大量行为。**`/tdd`** 和 **`/improve-codebase-architecture`** 都使用它。

## # 阶段边界

**阶段**是会话内的一块工作 —— 面试、实现、QA。在它们之间的**边界**处，您有五个选项，在它们之间选择是这个整个地图中最模糊的决定：

* 继续 —— 留在原地。不花成本，不损失任何东西。
* `/clear` — 清空窗口，当这里没有任何东西与接下来的内容相关时。
* `/handoff` — 写一个可移植的 markdown 文件。狭窄：仅用于**新的工具**、**新目录**、**同事**，或在**阶段中途**分叉一个副任务。它买来的是可移植性。
* 子代理 —— 向其自己的窗口发送一个范围紧密的任务并获取报告。
* `/compact` — 压缩此上下文并以此种子启动一个新会话。**默认**选项，位于树底而非第一次触及。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以获取有序的树 —— 五个问题、每个分支背后的推理，以及为什么主要来源的成本使 **Continue** 成为首先排除的选项。在**边界**处做出决定；在阶段中途，继续或将其余部分拆分为子代理。

## 独立

完全脱离主流程。

* `/grill-me` — 与 `/grill-with-docs` 相同的无情面试，但**无状态**：它不保存任何本地内容，也不构建 `CONTEXT.md`。当您**不在开发目录中工作**时使用它 —— 打磨计划、设计、写作、任何没有仓库在其下的东西。如果您在开发目录中，请改用 `/grill-with-docs`：它运行相同的面试并留下书面记录，所以严格来说它是更好的选择。
* `/grilling` — 面试原语本身：轮次、前沿、事实是代理的工作，决策是您的。`/grill-me` 和 `/grill-with-docs` 是两个命名的进入方式，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当您想要没有包装器的面试时才直接使用它。
* `/resolving-merge-conflicts` — 逐块处理进行中的合并或变基冲突，通过追溯到每方主要来源的**意图**来解决，而不是通过选择行，然后完成操作。它从不运行 `--abort`。独立且关闭所有流程：当您已经处于冲突中途时使用它。
* `/prototype` — 一个小的一次性程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。一次性是对如何编写代码的约束，而不是销毁它的承诺：答案会折叠进真实代码，原型本身作为**主要来源**保留在一个 `prototype/<name>` 分支上，该分支脱离主分支，从实现工单中指向它。它是主流程第 2 步的绕道，但任何设计问题在纸上难以确定时都可以使用它。
* **`/research`** — 将阅读的繁重工作委托给**后台代理**：它针对**主要来源**调查问题，然后在仓库中留下一个引用的 Markdown 文件。当它阅读时继续工作。它产生的文件是带到*主流程*中的 **`/grill-with-docs`** 的东西 —— 研究喂养思考，它不代替思考。
* `/to-questionnaire` — 当阻碍您的东西不在您的脑海中或代码库中，而在**别人**那里时，这会为他们写一份问卷供填写。这是 `/grill-me` 的逆过程：不是采访您关于主题，而是采访您关于**发送** —— 它要去给谁，您需要什么回来 —— 并将问题针对差距。返回的内容是 `/grill-with-docs` 或 `/to-spec` 的材料。
* `/wizard` — 用于只有**人类**才能执行的步骤：设置基础设施、配置凭据或 CI 密钥、点击通过不熟悉的第三方仪表板、运行一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL，捕获每个值，并将其写入 `.env` 和 GitHub 密钥 —— 这样该程序就不再是每次都要向代理重新解释的内容。由模型调用，因此代理在遇到只有您能通过的障碍时会立即使用它。如果代理本身可以完成，它应该；这是为了人类真正处于循环中的情况。
* `/wait-what` —— 修正未送达的消息。在对话中途，在任何其他技能内部使用它，代理会用您缺失的上下文，用简单的英语，使用 `CONTEXT.md` 词汇重新推销它刚才说的话。它在事后起作用；`/grill-with-docs` 是事前的疗法，因为早期达成的共同语言是阻止术语出现的根本原因。
* **`/teach`** — 在多个会话中使用当前目录作为有状态工作空间学习一个概念。
* `/writing-for-agents` — 编写代理消耗的文档的参考：技能、AGENTS.md、指向的文档。
