# 改进代码库架构

揭示架构摩擦并提出**深化机会**：将浅层模块转化为深层模块的重构。目标是实现可测试性和 AI 可导航性。

本命令*基于*项目的领域模型，并构建在共享的设计词汇之上：

* 使用 Skill 工具并调用 "codebase-design" 来获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口是测试表面"、"一个适配器 = 假设性接缝，两个 = 真实接缝"）。在每个建议中都使用这些术语，不要陷入 "组件"、"服务"、"API" 或 "边界" 的描述中。
* `CONTEXT.md` 中的领域语言为良好的接缝提供了命名；`docs/adr/` 中的 ADR 记录了本命令不应重新讨论的决策。

## 流程

### 1. 探索

扫描前的范围：YAGNI。深化模块之所以值得，是因为它能让未来的变更变得更容易，因此请重点关注最近发生变化的代码库部分。在查看之前，决定 *去哪里* 查看：

* 如果用户指定了方向（一个模块、一个子系统、一个痛点），就采纳它，并跳过下面的推断。
* 否则，回溯一段不错的提交历史（`git log --oneline`）以找到代码库的热点，即反复出现的文件和区域，并让这些路径首先吸引你的注意。如果变化分散且没有明显的热点，就扩大搜索范围。

首先阅读项目的领域术语表（`CONTEXT.md`）以及你将要触及的区域中的任何 ADR。

然后生成一个子代理来遍历代码库。不要遵循僵化的启发式规则；有机地探索并注意你在哪里感到摩擦：

* 在哪些地方，理解一个概念需要在许多小模块之间来回跳转？
* 哪些模块是**浅层**的，其接口几乎与实现一样复杂？
* 哪些地方为了可测试性而提取了纯函数，但真正的 bug 却隐藏在它们的调用方式中（缺乏**局部性**）？
* 哪些紧密耦合的模块在它们的接缝处发生了泄漏？
* 代码库的哪些部分未经过测试，或者难以通过当前接口进行测试？

对任何你怀疑是浅层的东西应用**删除测试**：删除它会集中复杂性，还是仅仅转移它？"是的，会集中"就是你想要的信号。

### 2. 将候选方案呈现为 HTML 报告

将一个独立的 HTML 文件写入操作系统临时目录，以免任何内容落入仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，以便每次运行都获得一个新文件。为用户打开它（Linux 上使用 `xdg-open <path>`，macOS 上使用 `open <path>`，Windows 上使用 `start <path>`）并告诉他们绝对路径。

报告使用 **Tailwind via CDN** 进行布局和样式设置，并使用 **Mermaid via CDN** 绘制图表，其中图/流程/序列可靠地传达了结构。将 Mermaid 与手工制作的 CSS/SVG 视觉效果混合使用：当关系呈图状（调用图、依赖关系、序列）时使用 Mermaid，当你想要更具编辑性质的内容时（质量图、剖面、折叠动画）使用手工构建的 div/SVG。每个候选方案都会获得一个**前后可视化**。要注重可视化。

对于每个候选方案，渲染一张卡片，包含：

* **文件**：涉及哪些文件/模块
* **问题**：为什么当前架构正在产生摩擦
* **解决方案**：对将要发生变化的简单描述
* **收益**：从局部性和杠杆的角度进行解释，以及测试将如何改进
* **前后对比图**：并排展示，手工绘制，展示浅层和深化的过程
* **推荐强度**：`Strong`（强）、`Worth exploring`（值得探索）、`Speculative`（推测性）之一，渲染为徽章

在报告末尾加上**首要推荐**部分：你会先处理哪个候选方案，以及为什么。

**使用 CONTEXT.md 词汇表中的领域术语，使用 `/codebase-design` 词汇表中的架构术语。** 如果 `CONTEXT.md` 定义了 "Order"，就谈论 "订单录入模块"，而不是 "FooBarHandler"，也不是 "订单服务"。

**ADR 冲突**：如果候选方案与现有的 ADR 相矛盾，只有在摩擦足够真实以至于值得重新审视该 ADR 时才将其揭示。在卡片中清楚地标记它（例如，一个警告提示：*"与 ADR-0007 相矛盾，但值得重新打开，因为…"*）。不要列出 ADR 禁止的每一个理论上的重构。

有关完整的 HTML 脚手架、图表模式和样式指南，请参阅 [HTML-REPORT.md](HTML-REPORT.md)。

现在还不要提出接口。在文件写入后，询问用户："你想探索其中的哪一个？"

### 3. 质询循环

一旦用户选中了一个候选方案，使用 Skill 工具并调用 "grilling" 来与他们一起梳理决策树：约束、依赖关系、深化后的模块形状、接缝后面是什么、哪些测试能存活下来。

决策确定时，副作用会内联发生；使用 Skill 工具并调用 "domain-modeling" 来保持领域模型与当前进度同步：

* **正在用一个 `CONTEXT.md` 中不存在的概念来命名深化后的模块？** 将该术语添加到 `CONTEXT.md`。如果文件不存在，则延迟创建。
* **在对话过程中厘清了一个模糊术语？** 当场更新 `CONTEXT.md`。
* **用户用具有决定性的理由拒绝了候选方案？** 提供一个 ADR，表述为：*"想让我把它记录为 ADR，以便未来的架构审查不再重新建议它吗？"* 只有当未来的探索者实际上需要该理由来避免重复建议时才提供；跳过短暂的理由（"现在不值得"）和显而易见的理由。
* **想为深化后的模块探索替代接口吗？** 调用 Skill 工具并传入 "codebase-design"，使用其"设计两次"的并行子代理模式。
