# 逻辑原型

一个单一、自包含的 HTML 文件（**可共享的演示**），允许任何人通过点击按钮来驱动状态模型。当问题涉及**业务逻辑、状态转换或数据形状**时使用：那种在纸上看起来合理，但一旦通过真实用例验证就会感觉不对劲的东西。

因为它是一个无需安装任何东西的单文件，你可以把它交给非开发者（设计师、产品经理、领域专家），让他们自己体验这个模型。因此，它使用的是他们的语言，而不是代码的语言。

## 何时适合使用这种形态

* 「我不确定这个状态机是否处理了 X 然后 Y 的边界情况。」
* 「这个数据模型真的能让我表示……这种情况吗？」
* 「我想在编写 API 之前先感受一下它应该是什么样子。」
* 任何希望**按下按钮并观察状态变化**的情况。

如果问题是「这应该是什么样子」，那这就是错误的分支。请使用 [UI.md](UI.md)。

## 流程

### 1. 说明问题

在编写代码之前，写下你要进行原型化的状态模型和问题。在演示的顶部写一段话（在可见的介绍中，而不仅仅是一个注释）。回答错误问题的逻辑原型是毫无意义的，因此要明确问题，以便无论用户现在是在观看还是稍后回来，都可以进行检查。

### 2. 将逻辑隔离在可移植的模块中

将实际逻辑（负责回答问题的部分）放入一个单独的 `<script>` 块中，编写为一个小的、纯模块，以便日后可以将其提取出来并放入真实的代码库中。它周围的页面是一次性的；而这个模块不是。

具体形态取决于问题：

* **纯 reducer**：`(state, action) => state`。当动作是离散事件且状态是单个值时，这是很好的选择。
* **状态机**：显式状态和转换。当「现在哪些动作是合法的」是问题的一部分时，这是很好的选择。
* **纯函数的集合**，作用于普通数据类型。当不存在隐含的当前状态，只有转换时，这是很好的选择。
* **具有清晰方法面的类或模块**，当逻辑真正拥有持续的内部状态时。

选择最适合所提出问题的形态，*而不是*最容易连接到页面的那种。保持纯粹：没有 DOM、没有 `document`、没有按钮处理程序直接进入其中。页面调用它；没有反向流动。这就是让原型在其生命周期之外仍有用的原因：一旦问题得到回答，经过验证的 reducer / 状态机 / 函数集就会自行提升到真实模块中。

### 3. 构建可共享的 HTML 文件

一个文件，纯 HTML/CSS/JS：没有框架、没有打包器、没有服务器，所有内容都内联，因此可以通过双击打开，并且即使在作为邮件附件转发时也能运行。任何人都应该能够通过打开它来运行它。

为非开发者编写。每个标签都使用**领域语言**，而不是代码：按钮和状态的展示方式要像业务描述，而不是 reducer。用通俗易懂的语言解释正在发生的事情。

用清晰的分层结构从上到下布局：

1. **标题和一行说明**，说明这个演示让你探索什么（第 1 步中的问题）。
2. **当前状态**：完整的相关状态，渲染为可读面板（带有标签的字段，而不是原始 JSON 转储），并在每次点击后重新渲染，以便变化可见。在帮助非开发者理解时，指出刚刚发生了什么变化。
3. **自由操作按钮**：每个动作一个按钮，始终可用，以便任何人都可以以任意顺序操作模型。每次点击都会触发相应的动作并重新渲染状态。
4. **引导式演练**：一组**场景**，每个标签一个。每个标签包含场景的简短通俗易懂的描述（它设定的情况以及需要观察什么），并在其下方是该场景的有序**需要点击的按钮**。每个步骤都是一个真实的按钮：点击它执行该动作并进入下一步。开始演练会重置到已知的初始状态，以确保场景每次都以相同的方式运行。

选择能够展示棘手情况的场景，即那些在纸上很难推理的情况：正常路径、棘手的边缘情况，以及对某些本应非法之事的尝试。

保持美观但克制：清晰的排版、充足的间距和一种强调色。没有动画，没有花哨的噱头：任何都不应干扰状态和按钮的展示。

### 4. 移交

把文件发给他们，或者为他们打开。他们会在任何时候浏览演练和自由操作；有趣的时刻是当他们说「等等，那不应该可能」或「嗯，我以为 X 会不同」的时候；这些是*想法*中的缺陷，这正是其全部意义所在。如果他们想要新的动作或场景，就添加它们。原型是会演变的。

### 5. 捕获答案和原型

一旦原型回答了其问题，捕获答案，然后按照 [SKILL](SKILL.md) 的描述捕获原型。针对逻辑的具体映射：经过验证的 reducer / 状态机 / 函数集会提升到真实模块中（决策被吸收）；HTML 外壳会附带到保留原型的丢弃分支，并且由于它是自包含的，因此在那里可以随时重新运行。

## 反模式

* **不要添加测试。** 需要测试的原型不再是原型。
* **不要连接到真实数据库。** 使用内存状态，除非问题专门涉及持久化。
* **不要泛化。** 不要「如果我们以后想支持 X 会怎样」。原型只回答一个问题。
* **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理程序，它就不再可提取。保持页面作为纯模块之上的薄壳。
* **不要使用框架、打包器或服务器。** 一个让接收者双击的文件；React 应用或开发服务器违背了「可共享」的初衷。
* **不要将 HTML 外壳发布到生产环境。** 页面是为手动点击而优化的。它背后的逻辑模块才是值得保留的部分。
