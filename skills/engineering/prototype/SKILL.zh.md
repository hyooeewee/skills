# 原型

原型是 **用来回答问题的一次性代码**。问题决定了其形态。

## 选择一个分支

确定正在回答哪个问题——通过用户的提示、周围的代码，或询问用户是否在场：

* **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可共享的单一 HTML 文件——包含自由操作按钮和选项卡式引导演练——通过状态机处理难以在纸上推理的情况，并允许非开发者进行操控。
* “它应该长什么样？” → [UI.md](UI.md)。在单个路由上生成几种根本不同的 UI 变体，可通过 URL 查询参数和浮动底部栏进行切换。

这两个分支会产生非常不同的产物——如果选错了，整个原型就浪费了。如果问题确实模棱两可且用户无法联系上，则默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 适用于两者的规则

1. 从第一天起就视为一次性代码，并明确标记。将原型代码放置在其实际使用位置附近（在其正在原型的模块或页面旁边），以便上下文显而易见——但要命名它，以便普通读者能看出它是一个原型，而不是生产代码。对于一次性 UI 路由，遵循项目已使用的任何路由约定；不要发明新的顶层结构。
2. **易于运行**。一个 UI 原型从项目任务运行器的一条命令开始——`pnpm <name>`，`python <path>`，`bun <path>` 等。一个逻辑演示是用户双击即可打开的单一 HTML 文件。无论哪种方式，启动它都不需要思考。
3. 默认不持久化。状态存在于内存中。持久化是原型正在 *检查* 的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，则使用一个临时数据库或一个名为 "PROTOTYPE — wipe me"（原型——抹掉我）的本地文件。
4. 跳过打磨。没有测试，除了使原型 *可运行* 所需的错误处理外，没有其他错误处理，没有抽象。目的是快速学习。
5. 暴露状态。在每次操作（逻辑）或每次变体切换（UI）后，打印或渲染完整的、相关的状态，以便用户可以看到发生了什么变化。
6. 完成后将其捕获。将任何经过验证的决策折叠到真实代码中，然后将原型本身作为 **主要来源** 进行捕获：将其提交到一次性分支（不在主分支中），并在实施问题中留下指向该分支的上下文指针。也要捕获答案——即裁决和它解决的问题——在问题或提交中。主分支仅保留经过验证的决策。
