# UI 原型

在单一路由上生成**几种截然不同的 UI 变体**，可通过浮动底部栏切换。用户在浏览器中来回切换变体，选一个（或从每个变体中借鉴一些部分），然后把其余的都丢弃。

如果问题涉及逻辑/状态而不是外观——那就走错分支了。请使用 [LOGIC.md](LOGIC.md)。

## 何时适合使用这种形态

* 这个页面应该长什么样？
* 我想在确定之前，先看看这个仪表盘的几种选项。
* 为设置界面尝试一种不同的布局。
* 每当用户本来会在脑海中花一天时间在三个模糊的线框稿之间做选择时。

## 两种子形态——强烈优先选择子形态 A

当 UI 原型**与应用的其余部分紧密贴合**时——真实的页头、真实的侧边栏、真实的数据、真实的密度——判断起来要容易得多。孤立的一次性路由就像一个真空环境：每个变体单独看都很好。只要存在一个可以承载变体的合理现有页面，就默认选择子形态 A。只有当原型确实没有就近的宿主页面时，才使用子形态 B。

### 子形态 A——对现有页面的调整（首选）

路由已经存在。变体在**同一条路由**上渲染，由 `?variant=` URL 搜索参数控制。现有的数据获取、参数和认证都保持不变——只有渲染部分会切换。这是默认方式；除非有特定理由，否则就选它。

如果原型面向的还不是一个页面，但*自然应当存在于某个页面内*（仪表盘的新区块、设置屏幕上的新卡片、现有流程中的新步骤）——那仍然是子形态 A。将变体挂载在宿主页面内部。

### 子形态 B——新页面（最后手段）

只有当被原型化的东西确实没有现有页面可以承载时，才使用这种形态——例如一个全新的顶级界面，或是一个无法嵌入任何合理位置的流程。

按照项目已有的路由约定创建一个**一次性路由**——不要发明新的顶级结构。给它命名时让它明显是一个原型（例如在路径或文件名中包含 `prototype` 一词）。沿用相同的 `?variant=` 模式。

在确定使用子形态 B 之前，做一次合理性检查：真的没有现有页面可以嵌入这个原型吗？一个空路由会隐藏设计问题，而一个有内容的路由会暴露它们。

在两种子形态中，浮动底部栏都是相同的。

## 流程

### 1. 明确问题并选择 N

默认提供 **3 个变体**。超过 5 个就不再是截然不同，而会变成噪音——到此为止。

在原型所在位置或文件顶部的注释中，用一行写下计划：

> 在现有 `/settings` 路由上，通过 `?variant=` 切换设置页面的三种变体。

无论用户是否打算反驳，这个办法都成立。

### 2. 生成截然不同的变体

起草每个变体。让每个变体都符合以下要求：

* 页面的目标以及它可以访问的数据。
* 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
* 一个清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**在结构上不同**——不同的布局、不同的信息层级、不同的主要操作方式，而不仅仅是不同的颜色。三个稍作调整的卡片网格不是 UI 原型，而是壁纸。如果两个草案过于相似，请根据明确的“不要使用卡片网格”的指导重做其中一个。

### 3. 将它们连接起来

在路由上创建一个单一的切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：将现有的数据获取逻辑全部保留在切换器之上；只有渲染的子树会随变体变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

### 4. 构建浮动切换器

一个固定在屏幕底部中央的小型横条，包含三部分：

* **左箭头**——切换到上一个变体（循环）。
* **变体标签**——显示当前变体的键，如果变体导出了名称，也显示名称。例如 `B — Sidebar layout`。
* **右箭头**——切换到下一个变体（循环）。

Behaviour:

* 点击箭头会更新 URL 搜索参数（使用框架的路由器——Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可以分享，并且在刷新后保持不变。
* 键盘：`←` 和 `→` 方向键也可以循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
* 在视觉上与页面区分开来（例如高对比度的胶囊形状、微妙的阴影），让人一眼看出它不是被评估设计的一部分。
* 在生产构建中隐藏——以 `process.env.NODE_ENV !== 'production'` 或等效检查作为开关，这样一次误合并的原型不会把该横条带给用户。

将切换器放在一个共享组件中，这样两种子形态都可以复用。把它放在项目中共享 UI 所在的位置。

### 5. 交接

给出 URL（以及 `?variant=` 键）。用户随时可以进行切换。有趣的反馈通常是\*\*“我想要 B 的页头，配上 C 的侧边栏”\*\*——这才是他们真正想要的设计。

### 6. 记录结果并清理

一旦某个变体胜出，记录结论——哪个变体以及为什么——然后按照 [SKILL](SKILL.md) 描述的方式记录原型。将胜出的变体合并到真实代码中，并把其余部分移到一次性分支上，而不是主分支：

* **子形态 A**——将获胜变体合并到现有页面；从主分支中移除落选变体和切换器。
* **子形态 B**——将获胜变体提升为正式路由；从主分支中移除一次性路由和切换器。

完整的变体集合是主要成果，所以它应该进入一次性分支，而不是垃圾桶——留在主分支上的变体组件和切换器会很快腐坏，并让下一位读者感到困惑。

## 反模式

* **仅在颜色或文案上不同的变体。** 那只是微调，不是原型。真正的变体在结构上有所不同。
* **在变体之间共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 则失去了意义。每个变体都应该可以自由地推翻布局。
* **将变体接入真实的变更操作。** 只读原型没问题。如果某个变体需要修改数据，请将它指向一个桩——问题在于“它应该长什么样”，而不是“后端是否正常工作”。
* **直接将原型提升到生产环境。** 变体代码是在原型约束下编写的（没有测试，错误处理最少）。在合并时，要正确地重写它。
