# UI 原型

在单一路由上生成**几种截然不同的 UI 变体**，可通过浮动底部栏切换。用户在浏览器中来回切换变体，选一个（或从每个变体中借鉴一些部分），然后把其余的都丢弃。

如果问题关乎逻辑/状态而非外观，则走错分支。使用 [LOGIC.md](LOGIC.md)。

## 何时适合使用这种形态

* 这个页面应该长什么样？
* 我想在确定之前，先看看这个仪表盘的几种选项。
* 为设置界面尝试一种不同的布局。
* 每当用户本来会在脑海中花一天时间在三个模糊的线框稿之间做选择时。

## 两种子形态：强烈偏好子形态 A

当 UI 原型**紧贴应用其余部分**时，更容易评判：真实的头部、真实的侧边栏、真实的数据、真实的密度。一个独立的一次性路由就是一个真空：每个变体单独看都很不错。只要有合理的现有页面可以托管变体，就默认使用子形态 A。只有在原型真的没有邻近的归宿时，才考虑子形态 B。

### 子形态 A：调整现有页面（首选）

路由已经存在。变体在**同一路由**上渲染，由 `?variant=` URL 搜索参数控制。现有的数据获取、参数和认证都保持不变。只有渲染部分会切换。这是默认选项；除非有特定原因，否则选择它。

如果原型用于某样还没有页面但*自然适合放在其中*的东西（仪表盘的新区块、设置屏幕上的新卡片、现有流程中的新步骤），它仍然是子形态 A。将变体挂载到宿主页面中。

### 子形态 B：新建页面（最后手段）

仅在要原型化的东西真的没有现有页面可嵌入时使用（例如一个全新的顶层界面，或无法嵌入任何合理位置的流程）。

按照项目现有的路由约定创建一个**一次性路由**。不要发明新的顶层结构。命名时要让人一眼看出是原型（例如在路径或文件名中包含 `prototype` 一词）。使用相同的 `?variant=` 模式。

在确定使用子形态 B 之前，做一次合理性检查：真的没有现有页面可以嵌入这个原型吗？一个空路由会隐藏设计问题，而一个有内容的路由会暴露它们。

在两种子形态中，浮动底部栏都是相同的。

## 流程

### 1. 明确问题并选择 N

默认为 **3 个变体**。超过 5 个就会停止产生显著差异，开始变成噪音，所以限制在 5 个以内。

在原型所在位置或文件顶部的注释中，用一行写下计划：

> 在现有 `/settings` 路由上，通过 `?variant=` 切换设置页面的三种变体。

无论用户是否打算反驳，这个办法都成立。

### 2. 生成截然不同的变体

起草每个变体。让每个变体都符合以下要求：

* 页面的目标以及它可以访问的数据。
* 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
* 一个清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上有所不同**：不同的布局、不同的信息层级、不同的主要交互方式，而不仅仅是不同的颜色。三个稍作调整的卡片网格并不是 UI 原型，它只是壁纸。如果两个草稿过于相似，请用明确的“不要使用卡片网格”的指示重做一个。

### 3. 将它们连接起来

在路由上创建一个单一的切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：将现有的数据获取逻辑全部保留在切换器之上；只有渲染的子树会随变体变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

### 4. 构建浮动切换器

一个固定在屏幕底部中央的小型横条，包含三部分：

* **左箭头**：循环到上一个变体（循环切换）。
* **变体标签**：显示当前变体键，如果变体导出了名称，也显示该名称。例如 `B (Sidebar layout)`。
* **右箭头**：向前循环（循环切换）。

Behaviour:

* 点击箭头会更新 URL 搜索参数（使用框架的路由器，例如 Next.js 上的 `router.replace`，React Router 上的 `navigate` 等），以便变体可以分享且刷新后保持稳定。
* 键盘：`←` 和 `→` 方向键也可以循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
* 在视觉上与页面区分开来（例如高对比度的胶囊形状、微妙的阴影），让人一眼看出它不是被评估设计的一部分。
* 在生产构建中隐藏：通过 `process.env.NODE_ENV !== 'production'` 或等效检查进行门控，这样意外的原型合并就无法将横条发送给用户。

将切换器放在一个共享组件中，这样两种子形态都可以复用。把它放在项目中共享 UI 所在的位置。

### 5. 交接

暴露 URL（以及 `?variant=` 键）。用户每次到达时都会来回切换。有趣的反馈通常是 **"我想要 B 的头部和 C 的侧边栏"**，这才是他们实际想要的设计。

### 6. 记录结果并清理

一旦某个变体胜出，记录答案（哪个变体以及原因），然后按照 [SKILL](SKILL.md) 的描述捕获原型。将获胜者合并到真实代码中，将其余部分移到一次性分支上，而不是主分支：

* **子形态 A**：将获胜者合并到现有页面；从主分支中移除失败的变体和切换器。
* **子形态 B**：将获胜变体提升为真实路由；从主分支中移除一次性路由和切换器。

完整的变体集是主要来源，所以它应该放在一次性分支上，而不是垃圾桶里，因为留在主分支中的变体组件和切换器会迅速腐烂并让下一位读者感到困惑。

## 反模式

* **仅在颜色或文案上不同的变体。** 那只是微调，不是原型。真正的变体在结构上有所不同。
* **在变体之间共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 则失去了意义。每个变体都应该可以自由地推翻布局。
* **将变体连接到真实变更**。只读原型没问题。如果变体需要变更，将其指向存根：问题在于“它应该长什么样”，而不是“后端是否工作”。
* **直接将原型提升到生产环境。** 变体代码是在原型约束下编写的（没有测试，错误处理最少）。在合并时，要正确地重写它。
