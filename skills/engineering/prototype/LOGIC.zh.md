# 逻辑原型

一个小巧的交互式终端应用，让用户手动驱动状态模型。当问题涉及**业务逻辑、状态转换或数据结构**时使用此工具——那种在纸面上看起来合理，但一旦经过实际案例推演就会感觉不对劲的东西。

## 何时采用此形态

* 我不确定这个状态机是否处理了 X 然后 Y 的边缘情况。
* 这个数据模型实际上是否允许我表示这种情况……
* 我想在编写之前摸索一下 API 应该长什么样。
* 任何用户想要**按按钮并观察状态变化**的场景。

如果问题是“这应该长什么样”——那就选错分支了。使用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在编写代码之前，写下你要原型化的状态模型和问题。一段话，放在原型的 README 中或文件顶部的注释里。回答了错误问题的逻辑原型纯属浪费——让问题明确化，以便稍后检查，无论用户现在是否在观看，或者稍后 AFK 回来。

### 2. 选择语言

使用宿主项目使用的任何语言。如果项目没有明显的运行时（例如文档仓库），请询问。

匹配项目现有的工具约定——不要仅仅为了原型而添加新的包管理器或运行时。

### 3. 在可移植模块中隔离逻辑

将实际逻辑——即回答问题的部分——隐藏在一个小巧、纯净的接口背后，以便稍后可以提取并放入真实代码库。周围的 TUI 是一次性使用的；逻辑模块不应该如此。

正确的形态取决于问题：

* **一个纯 reducer**——`(state, action) => state`。当动作是离散事件且状态是单一值时很好用。
* **一个状态机**——明确的状态和转换。当“此刻哪些动作是合法的”是问题的一部分时很好用。
* **一组纯函数**，作用于普通数据类型。当没有隐含的当前状态——只有转换时很好用。
* **一个具有清晰方法接口的类或模块**，当逻辑真正拥有持续存在的内部状态时。

选择最符合所提问题的形态，*而不是*哪个最容易连接到 TUI。保持其纯净：无 I/O，无终端代码，无 `console.log` 用于控制流。TUI 导入它并调用它；没有数据流向反方向。

这就是原型在其生命周期之外仍有用的原因：当问题得到解答后，经过验证的 reducer / 状态机 / 函数集可以独立提升到真实模块中。

### 4. 构建最小的暴露状态的 TUI

将其构建为一个**轻量级 TUI**——在每个时刻，清除屏幕（`console.clear()` / `print("\033[2J\033[H")` / 等效命令）并重新渲染整个帧。用户应该始终看到一个稳定的视图，而不是不断增长的滚动记录。

每个帧有两个部分，按此顺序排列：

1. **当前状态**，格式化打印且易于 diff（每行一个字段，或格式化 JSON）。使用 **粗体** 表示字段名或章节标题，使用 **暗淡** 表示不太重要的上下文（时间戳、ID、派生值）。原生 ANSI 转义码即可——`\x1b[1m` 粗体，`\x1b[2m` 暗淡，`\x1b[0m` 重置。除非项目中已经有样式库，否则不需要引入。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 推进时钟  [q] 退出`。粗体表示按键，暗淡表示描述，反之亦然——只要阅读清晰即可。

Behaviour:

1. **初始化状态**——一个单一内存对象/结构体。在启动时渲染第一帧。
2. **一次读取一个按键（或一行）**，分发给一个改变状态的处理器。
3. **重新渲染**每一个动作后的完整帧——不要追加，要替换。
4. **循环直到退出。**

整个帧应该能容纳在一个屏幕上。

### 5. 使其可以通过一条命令运行

向项目的现有任务运行器添加一个脚本（`package.json` 脚本、`Makefile`、`justfile`、`pyproject.toml`）。用户应该运行 `pnpm run <原型名称>` 或等效命令——永远不需要记住路径。

如果宿主项目没有任务运行器，只需将命令放在原型的 README 顶部。

### 6. 移交

给用户运行命令。他们会自己驱动它；有趣的时刻是当他们说“等等，那不应该可能”或“哈，我假设 X 会不同”——这些是*想法*中的 bug，这就是全部意义所在。如果他们想添加新动作，就添加。原型会演变。

### 7. 捕获答案和原型

一旦原型回答了其问题，捕获答案，然后按照 [SKILL](SKILL.md) 描述的方式捕获原型。逻辑特定的映射：经过验证的 reducer / 状态机 / 函数集提升到真实模块（决策，被吸收）；TUI shell 随之带到废弃分支，该分支将原型作为主要来源。

## 反模式

* **不要添加测试。** 需要测试的 prototype 就不再是原型了。
* **不要将其连接到真实数据库。** 使用内存存储，除非问题专门关于持久化。
* **不要泛化。** 没有“如果我们以后想支持 X 会怎样”。原型回答一个问题。
* **不要将逻辑和 TUI 混淆在一起。** 如果 reducer / 状态机引用了 `console.log`、提示符或终端转义码，它就不再可移植了。将 TUI 保持为纯模块的薄壳。
* **不要将 TUI shell 部署到生产环境。** 该 shell 专为从终端手动驱动而优化。其背后的逻辑模块才是值得保留的部分。
