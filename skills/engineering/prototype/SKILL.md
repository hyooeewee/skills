# 原型

原型是**一次性代码，用来回答问题**。问题决定其形态。

## 选择分支

使用用户的提示、周围的代码，或者询问用户是否在场，来确定正在回答哪个问题：

* "这个逻辑/状态模型感觉对吗？" → [LOGIC.md](LOGIC.md)。构建一个可分享的 HTML 文件（包含自由播放按钮和带标签的引导式演练），通过将状态机推演到那些在纸上难以推理的情况，并让非开发者能够驱动它。
* **“这应该长什么样？”** → [UI.md](UI.md)。在单个路由上生成几种截然不同的 UI 变体，通过 URL 查询参数和浮动底部栏进行切换。

两个分支产生的产物差异很大，所以如果选错了，整个原型就浪费了。如果问题真正模棱两可且用户联系不上，则默认选择更符合周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 适用于两者的规则

1. **从一开始就是一次性代码，并明确标记。** 将原型代码放置在其实际使用的地方附近（与其原型化的模块或页面相邻），以便上下文显而易见，但将其命名得让普通读者能看出这是一个原型，而非生产代码。对于一次性 UI 路由，遵循项目已使用的任何路由约定；不要发明新的顶层结构。
2. **运行极其简单。** UI 原型从项目任务运行器中的一个命令开始：`pnpm <name>`, `python <path>`, `bun <path>` 等。逻辑演示是用户双击的单个 HTML 文件。无论如何，启动它都不需要思考。
3. **默认不持久化。** 状态存在于内存中。持久化是原型要*检查*的内容，而不是它应该依赖的内容。如果问题明确涉及数据库，请连接一个草稿数据库或本地文件，其名称带有清晰的“PROTOTYPE, wipe me”。
4. **跳过打磨。** 不写测试，除了让原型*能够运行*所需的错误处理之外，不做错误处理，也不做抽象。重点是快速学到东西。
5. **让状态可见。** 每次操作（逻辑）或每次变体切换（UI）后，打印或渲染完整的相关状态，让用户看到发生了什么变化。
6. **完成后进行捕获。** 将任何已验证的决定融入真实代码，然后将原型本身捕获为**主要来源**：将其提交到一次性分支（脱离主分支），并在实施问题上留下指向该分支的上下文指针。也要在问题或提交中捕获答案（裁决和它解决的问题）。主分支仅保留已验证的决定。
