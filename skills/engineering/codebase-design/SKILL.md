# 代码库设计

设计**深度模块**：将大量行为放在小接口之后，置于干净的接缝处，并可通过该接口测试。无论在哪里设计或重构代码，都使用这套语言和原则。目标是让调用方获得杠杆效应，让维护者获得局部性，让所有人都获得可测试性。

## 词汇表

精确使用这些术语：不要用 "component"（组件）、"service"（服务）、"API" 或 "boundary"（边界）来替换。一致的语言是关键所在。

**模块**：任何拥有接口和实现的事物。刻意保持规模无关：函数、类、包或跨层级的切片。*避免*：unit（单元）、component（组件）、service（服务）。

**接口**：调用者正确使用模块所需了解的一切：类型签名，但也包括不变量、排序约束、错误模式、所需配置和性能特征。*避免*：API、signature（签名）（太狭隘，它们仅指类型级的表面）。

**实现**：模块内部的内容，即代码体。与**适配器**不同：某物可以是一个带有大实现的适配器（Postgres 仓库），也可以是一个带有小实现的适配器（内存中的假数据）。当话题是接缝时，使用 "adapter"；否则使用 "implementation"。

**深度**：接口处的杠杆效应。调用者（或测试）在必须学习的接口单位上可以执行的行为量。当大量行为隐藏在小接口背后时，模块是**深**的；当接口几乎与实现一样复杂时，是**浅**的。

**接缝** *(Michael Feathers)*：在不编辑该位置的情况下改变行为的地方；模块接口所在的*位置*。接缝放在哪里本身就是一个设计决定，与它背后是什么是不同的。*避免*：boundary（边界）（与 DDD 的限界上下文含义重叠）。

**适配器**：在接缝处满足接口的具体事物。描述的是*角色*（它填补的槽位），而不是实质（内部有什么）。

**杠杆效应**：调用者从深度中获得的东西。每单位接口的学习带来更多的能力。一个实现可以在 N 个调用点和 M 个测试中偿还价值。

**局部性**：维护者从深度中获得的东西。变更、错误、知识和验证集中在一点，而不是分散在各个调用方。一次修复，处处生效。

## 深度与浅层

**深度模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时，请问：

* 我能减少方法的数量吗？
* 我能简化参数吗？
* 我能把更多复杂性藏在内部吗？

## 原则

* **深度是接口的属性，而不是实现的属性。** 一个深度模块可以由小的、可模拟的、可交换的部分内部组成；它们只是不是接口的一部分。一个模块可以有**内部接缝**（对其实现私有，由其自己的测试使用）以及其接口处的**外部接缝**。
* **删除测试。** 想象删除这个模块。如果复杂性消失了，那它只是个传话筒。如果复杂性重新分散到 N 个调用方，那它正在发挥价值。
* **接口就是测试面。** 调用方和测试跨越同一条接缝。如果你想要测试*绕过*接口，这个模块的形状可能不对。
* **一个适配器意味着假想的接缝；两个适配器意味着真实的接缝。** 除非确实有东西会跨接缝变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 方法越少 = 需要的测试越少。参数越少 = 测试设置越简单。

## 关系

* 一个**模块**恰好有一个**接口**（它向调用方和测试呈现的表面）。
* **深度**是**模块**的属性，相对于其**接口**来衡量。
* **接缝**是**模块**的**接口**所在之处。
* **适配器**位于**接缝**处，并满足**接口**。
* **深度**为调用方带来**杠杆效应**，为维护者带来**局部性**。

## 被拒绝的框架

* **将深度定义为实现行数与接口行数之比**（Ousterhout）：这会奖励注水实现。我们改用深度即杠杆。
* **"Interface" 指 TypeScript 的 `interface` 关键字或类的公共方法**：太狭隘：此处的接口包括调用者必须了解的所有事实。
* **「边界」**：与 DDD 的限界上下文含义重叠。请说**接缝**或**接口**。
