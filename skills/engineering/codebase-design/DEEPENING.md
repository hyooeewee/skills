# 深化

如何在给定其依赖的情况下安全地深化一组浅层模块。假设 [SKILL.md](SKILL.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

在评估一个可深化的候选模块时，先对其依赖进行分类。类别决定了深化后的模块如何跨越其接缝进行测试。

### 1. 进程内

纯计算、内存状态，无 I/O。总是可深化的：合并模块并通过新接口直接测试。不需要适配器。

### 2. 本地可替代

具有本地测试替身的依赖（Postgres 用 PGLite，内存文件系统）。如果存在替身，则可以深化。深化后的模块在测试套件中运行替身进行测试。接缝是内部的；在模块的外部接口处没有端口。

### 3. 远程但自有（端口与适配器）

你在网络边界之外拥有的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深层模块拥有逻辑；传输以**适配器**的形式注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议形式：*“在接缝处定义一个端口，为生产环境实现 HTTP 适配器，为测试实现内存适配器，这样逻辑就位于同一个深层模块中，即使它部署在网络中。”*

### 4. 真正的外部（模拟）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的端口；测试提供模拟适配器。

## 接缝纪律

* **一个适配器意味着一个假设的接缝；两个适配器意味着一个真实的接缝。** 除非至少有两个适配器是合理的（通常是生产环境 + 测试），否则不要引入端口。单一适配器的接缝只是间接层。
* **内部接缝与外部接缝。** 深层模块可以同时拥有内部接缝（对其实现私有，供自己的测试使用）和接口处的外部接缝。不要仅仅因为测试使用了内部接缝，就通过接口暴露它们。

## 测试策略：替换，而不是分层

* 一旦在深化后模块的接口处存在测试，旧模块上的单元测试就变成了浪费；删除它们。
* 在深化后模块的接口处编写新测试。**接口就是测试面**。
* 测试通过接口断言可观察的结果，而非内部状态。
* 测试应该能经受住内部重构，因为它们描述的是行为，而不是实现。如果一个测试在实现改变时必须改变，说明它测试的范围已经超出了接口。
