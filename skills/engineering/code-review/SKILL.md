对 `HEAD` 与用户提供的固定点之间的 diff 进行双轴审查：

* **标准**：代码是否符合此仓库记录的编码标准？
* **规格**：代码是否忠实实现了原始 issue / 规格？

两个轴都作为**并行子代理**运行，这样它们不会污染彼此的上下文，然后此技能汇总它们的发现。

问题追踪器应该已经提供给你。如果 `docs/agents/issue-tracker.md` 缺失，请告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所说的任何内容都是固定点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果他们没有指定一个，就询问他们。

将 diff 命令固定为：`git diff <fixed-point>...HEAD`（三点形式，因此与 merge-base 进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

在继续之前，确认固定点已解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的引用或空的 diff 应该在这里失败，而不是在两个并行子代理内部。

### 2. 识别 spec 来源

按以下顺序查找原始 spec：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. 位于 `docs/`、`specs/` 或 `.scratch/` 下、与分支名或功能匹配的 spec 文件。
4. 如果什么都没找到，请询问用户 spec 在哪里。如果他们说没有，**Spec** 子代理将跳过并报告"no spec available"。

### 3. 识别标准来源

仓库中任何记录了代码编写规范的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库记录的任何内容之上，标准轴始终携带以下**坏味道基线**：一组即使在仓库没有记录任何内容时也适用的 Fowler 坏味道（*Refactoring*，第 3 章）。两条规则约束它：

* **仓库优先。** 文档化的仓库标准始终优先；如果它认可了基线会标记的内容，则抑制该坏味道。
* **始终是判断性的。** 每种坏味道都是一个带标签的启发式方法（"可能的 Feature Envy"），从来不是硬性违规。像这里的任何标准一样，跳过任何工具已经强制执行的内容。

每种坏味道的读法是*它是什么* → *如何修复*；将其与 diff 进行比对：

* **神秘名称**：函数、变量或类型的名称没有揭示它做什么或包含什么。→ 重命名它；如果没有诚实的名字出现，设计就模糊不清。
* **重复代码**：相同的逻辑形状出现在更改中的多个代码块或文件中。→ 提取共享形状，从两者调用。
* **特性嫉妒**：一个触及另一个对象数据多于其自身的方法。→ 将方法移到它嫉妒的数据上。
* **数据团块**：相同的几个字段或参数一直一起出现（一个想要诞生的类型）。→ 将它们打包成一个类型，传递那个类型。
* **原始痴迷**：一个原始类型或字符串代表了一个值得自己类型的领域概念。→ 给这个概念它自己的小类型。
* **重复的开关**：相同的 `switch`/`if` 级联在相同类型上跨越更改重复出现。→ 用多态替换，或一个两个站点都共享的映射。
* **散弹手术**：一个逻辑更改迫使 diff 中许多文件出现分散的编辑。→ 将更改收集到一个模块中。
* **发散变更**：一个文件或模块被编辑了几次不相关的理由。→ 拆分，以便每个模块为一个理由更改。
* **推测的一般性**：为 spec 没有需要的添加的抽象、参数或钩子。→ 删除它；内联回退直到出现真实需求。
* **消息链**：调用者不应该依赖的长 `a.b().c().d()` 导航。→ 在第一个对象上隐藏遍历，在一个方法背后。
* **中间人**：一个主要只是继续委托的类或函数。→ 切断它，直接调用真实目标。
* **拒绝继承**：一个忽略或覆盖它继承的大部分内容的子类或实现者。→ 放弃继承，使用组合。

### 4. 并行启动两个子代理

**标准子代理提示**应包括：

* 完整的 diff 命令和提交列表。
* 你在步骤 3 中找到的标准源文件列表，**加上步骤 3 的坏味道基线**完整粘贴（子代理没有其他访问方式）。
* 任务简报："报告，在每个相关文件/代码块中，(a) diff 违反记录标准的每个地方：引用标准（文件 + 规则）；以及 (b) 你发现的任何基线坏味道：命名它并引用代码块。区分硬性违规与判断性调用：记录的标准违规可以是硬性的，但基线坏味道总是判断性的，并且记录的仓库标准会覆盖基线。跳过任何工具强制执行的内容。400 词以内。"

**规格子代理提示**应包括：

* diff 命令和提交列表。
* spec 的路径或获取到的内容。
* 任务简报："报告：(a) spec 要求但缺失或不完整的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现看起来有误的需求。为每条发现引用 spec 中的对应行。400 词以内。"

如果 spec 缺失，跳过 Spec 子代理并在最终报告中注明这一点。

### 5. 汇总

在 `## 标准` 和 `## 规格` 标题下展示两个报告，逐字或轻度清理。**不要**合并或重新排序发现，因为两个轴是有意分开的（见 *为什么是两个轴*）。

以一行摘要结束：每个轴的总发现数，以及每个轴内最差的问题（如果有）。不要在轴之间选出单一获胜者：那就是分离旨在防止的重新排序。

## 为什么是两个轴

一项变更可以顺利通过一个轴，却在另一个轴上失败：

* 遵循了所有标准但实现了错误内容的代码 → **Standards 通过，Spec 失败。**
* 完全按照 issue 的要求实现但破坏了项目约定的代码 → **Spec 通过，Standards 失败。**

分开报告它们，可以防止一个轴掩盖另一个轴。
