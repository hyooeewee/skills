一个模糊的想法已经出现——对一个代理会话来说过于庞大，而且被迷雾包裹：从这里到**目的地**的路尚不可见。寻路（Wayfinding）就是找到这条路，而不是径直冲向目的地。本技能将路线绘制为仓库问题跟踪器上的**共享地图**，然后逐个处理其中的**决策工单**——这些工单的解决结果是一个决策，而非一段要执行的建设任务——直到路线清晰为止。

目的地因具体工作而异，而为它命名是制图的第一步——它会塑造每一张工单。它可能是一份要交接并迭代的规格说明，一个在规划开始前要锁定的决策，或一个就地实施的变更，比如数据结构迁移。地图与领域无关——工程工作、课程内容，任何符合这种形态的工作都可以。

## 规划，而不是执行

Wayfinder 默认是**规划**性的：每张工单解决一个决策；当路径清晰时，地图就完成了——在有人去执行之前，没有任何需要再决策的事项。那种直接开干的冲动，通常表明你已经到达地图的边缘，是时候交接了。一个工作项可以在其 **Notes** 中覆盖这个默认设定——把执行也纳入地图本身——但若没有这样做，就产出决策，而不是交付物。

## 按名称引用

每张地图和每张工单都是一个 issue，因此它有一个**名称**——即其标题。在人类阅读的所有内容里——叙述、地图中的 Decisions-so-far——都应使用该名称来引用，绝不要使用裸露的 id、编号或 slug。一墙的 `#42, #43, #44` 难以阅读；名称则一眼可读。id 和 URL 并不会消失——名称包裹着它的链接——但它们位于*名称内部*，永远不会代替名称。

## 地图

地图是此仓库问题跟踪器上的一个单一 issue，带有 `wayfinder:map` 标签——它是权威工件。它的工单是地图的子 issue。

地图是一个**索引**，而不是存储库。它列出已做出的决策，并指向保存其细节的工单；一个决策只存在于一个地方——它的工单——因此地图永远不复述它，只做概要并链接过去。

**地图、其子工单、阻塞关系以及前沿查询在物理上位于何处，取决于具体的跟踪器。** 问题跟踪器应该已经提供给你。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档中的 "Wayfinding operations" 部分，了解*这个*仓库如何表达它们。如果没有提供跟踪器，默认使用本地 Markdown 跟踪器。

### 地图主体

整个地图以低分辨率呈现，每个会话加载一次。开放的工单**不**会被列出——它们是开放的子 issue，通过查询找到。

```markdown
## Destination

<what reaching the end of this map looks like — the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index — one line per closed ticket: enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link) — <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每张工单都是地图的一个**子 issue**；跟踪器的 issue id 就是其身份。它的正文是问题本身，大小适配一个 100K token 的代理会话：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单都带有一个 `wayfinder:<type>` 标签——取值之一为 `research`、`prototype`、`grilling`、`task`（参见 [工单类型](#ticket-types)）。

一个会话**认领**工单的方式是，在任何工作开始**之前**，先将它指派给驱动地图的开发者，这样并发的会话就会跳过它。被指派者*就是*认领：一张开放且未被指派的工单就是未被认领的。

阻塞使用跟踪器的**原生**依赖关系——这一点至关重要，因为它会在跟踪器自身的 UI 中*可视化*地呈现前沿，让人无需打开地图就能看到哪些可以领取。只有缺少原生阻塞的跟踪器才会退回到正文约定。当一张工单的所有阻塞工单都关闭时，它就是**未阻塞**的；**前沿**就是那些开放、未阻塞、未被认领的子 issue——已知领域的边缘。

答案不是正文的一部分——它在解决工单时被记录（参见 [推进地图](#work-through-the-map)）。解决工单过程中创建的资产从 issue 中链接出来，而不是粘贴进去。

## 工单类型

每张工单要么是 **HITL**——人在回路中，与一位能为自己发声的人共同完成——要么是 **AFK**，由代理单独驱动。HITL 工单只能通过这种实时交流来解决；代理绝不能代替人类一方（一个自己回答自己问题的 grilling 代理已经违背了这一点）。

* **Research**（AFK）：阅读文档、第三方 API 或本地资源（如知识库），以揭示某个决策所等待的事实。由调用带有 "research" 的 Skill 工具的子代理解决。当需要当前工作目录之外的知识时使用。
* **Prototype**（HITL）：通过制作一个廉价、粗糙、具体的工件来让讨论有物可依，从而提高讨论的保真度——一份大纲、一个粗略的版本、一个桩，或 UI/逻辑代码，方法是调用带有 "prototype" 的 Skill 工具。将原型作为资产链接出来。当关键问题是"它应该看起来如何"或"它应该如何表现"时使用。
* **Grilling**（HITL）：对话。默认情况。始终调用 Skill 工具两次，分别用于 "grilling" 和 "domain-modeling"。
* **Task**（HITL 或 AFK）：必须在做出*决策*之前完成的手动工作——没有要决策、做原型或研究的内容，但讨论会被阻塞直到完成。注册一个服务以便评判其 API、开通访问权限、移动数据以便看清其形态。这是唯一一个*执行*而非决策的类型——它通过解除某个决策的阻塞来赢得自己的位置，而不是通过交付目的地。代理在可以的地方独自驱动它（AFK）；否则它会交给人类一份精确的检查清单（HITL）。工作完成时即被解决；答案记录完成的工作，以及后续工单所依赖的任何结果事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图是*故意*不完整的：不要绘制你还看不到的东西。活跃工单之外是**战争迷雾**——你能感觉到即将到来但尚无法确定的决策与调查的模糊景象，因为它们悬在仍然开放的问题上。解决一张工单会清除它前方的迷雾，将当下已经可明确的内容升级为新的工单——一次一张，直到通往目的地的道路清晰且不再有剩余工单。

地图的 **Not yet specified（尚未指定）** 部分就是写下这种模糊景象的地方：怀疑的问题、日后要重新审视的领域。它是*朝向*目的地的未发现前沿——这里的一切都在范围内，只是还不够清晰到可以开票。根据视野所及，可以写得粗略或完整；它同时也是一个路标，让协作者了解这个工作项正朝哪个方向前进。

**迷雾还是工单？** 判断标准是，你现在能否精确地陈述这个问题——*而*不是你现在能否回答它。

* **开票，当**问题已经清晰——即使它被阻塞，你暂时还不能采取行动。
* **尚未指定，当**你还无法如此清晰地表述它时。不要把迷雾预先切成工单大小的碎片：它比工单更粗糙，一旦前沿推进到某一片迷雾，它可能升级为多张工单，也可能一张都不会升级。

\*\*Not yet specified（尚未指定）\*\*排除已经决定的内容（Decisions so far）、已经是活跃工单的内容，以及范围之外的内容（下一节）。

## 范围之外

迷雾只会*朝向*目的地聚集。目的地划定了范围，因此超出它的工作就是**范围之外**——它不是迷雾，也不属于 **Not yet specified（尚未指定）**。它在地图上拥有自己的 \*\*Out of scope（范围之外）\*\*部分：你自觉排除在*这个*工作项之外的工作。是范围，而不是清晰度，让它落到这里。

范围之外的工作永远不会升级——前沿停在目的地——因此只有当目的地被重新划定后，它才会回归，而且是以一个全新的工作项形式，而不是恢复原工作。

将某事物裁定为范围之外是一种划定范围的行为，而不是路线上的一个步骤。当一张已存在的工单被发现位于目的地之后——在绘制地图时被错误地划入，或因一项决议而暴露——**关闭它**（已关闭的工单明确地不在前沿）并在 **超出范围** 部分留下一行：要点加上它为何超出范围，并链接到已关闭的工单。它不应进入 **截至目前的决定**，后者记录的是实际走过的路线——范围边界不是其上的一步。

## 调用

两种模式。无论哪种方式，**每场会话最多只解决一张工单**——研究工单除外。

### 绘制地图

用户以一个粗略的想法发起。

1. **为目的地命名。** 调用 Skill 工具两次，分别用于 "grilling" 和 "domain-modeling"，以确定这张地图要通往何处——规格、决策或变更。目的地划定了范围，因此它最先被确定。
2. **绘制前沿。** 再次盘问，这次采用 **广度优先**：在整个空间展开，而不是深入任何一条线索，浮现出未决决策和当前可采取的第一步。**如果这没有浮现出任何迷雾**——通往目的地的道路已经清晰，整个旅程足够小，可以在一场会话内完成——你就不需要地图。停下来，询问用户希望如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填写目的地和备注，「截至目前的决定」留空，将迷雾勾勒进 **尚未明确**。
4. **创建你现在就能明确的工单**，作为地图的子问题——然后在 **第二遍** 中连接阻塞边（问题需要先有 id 才能互相引用）。连接将它们分类为前沿和被阻塞的；所有你还不能明确的工单留在迷雾中——即 **尚未明确** 部分。
5. **启动研究子代理。** 对于你刚刚创建的每张 `research` 工单，启动一个调用带有 "research" 的 Skill 工具的子代理来并行解决它，将其发现捕获在一个一次性的 `research/<name>` 分支上，并附带来自工单的上下文指针。
6. 停下——绘制地图是一次会话的工作；它不会手动解决任何问题。

### 按图推进

用户通过地图（URL 或编号）发起调用。工单是 **可选的**——如果没有指定，由你选择下一个决策，而不是用户。

1. 加载 **地图**——概览视图，而不是每张工单的完整正文。
2. 选择工单。如果用户指定了某一张，就使用它。否则按顺序取第一张前沿工单。**认领它**：在任何工作开始前将它分配给自己。
3. 解决它——**按需放大**：按需获取任何相关或已关闭工单的完整正文；为 `## Notes` 块中提到的技能调用 Skill 工具。如有疑问，调用 Skill 工具两次，分别用于 "grilling" 和 "domain-modeling"。
4. 记录解决结果：将答案作为 **决议评论** 发布，**关闭** 问题，并将 **上下文指针** 追加到地图的「截至目前的决定」。
5. 添加新浮现的工单（先创建后连接）；将任何已被答案明确化的迷雾转正，并从 **尚未明确** 中清除每个已转正的区域，使它只作为新工单存在。如果答案揭示一张工单——这张或另一张——位于目的地之后，**将其裁定为超出范围**，而不是在路线中解决它。如果该决定使地图的其他部分失效，则更新或删除这些工单。

用户可能会并行运行未被阻塞的工单，因此要预期其他会话会同时编辑跟踪器。
