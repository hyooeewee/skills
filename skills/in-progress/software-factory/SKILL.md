**软件工厂**是一个代理系统，将工单、PR 和计划转化为合并的代码，部署在用户选择的远程基础设施上。这项技能是设计软件工厂的语言。讨论或白板设计工厂时，仅使用这些术语；当用户想用 *Avoid* 下的词时，给出规范术语。

## 任务与运行

**任务**：工厂执行的一类工作，定义一次、多次运行：审查、探索、实现、棘轮。任务可作用于工单、PR 或整个代码库。*避免*：用 job、workflow、action 命名任务。CI 厂商的工作流文件及其 job 是任务的接线处，而非任务本身。

**触发器**：启动运行的事件：工单追踪器或 Git 托管的变更、编排器中的时钟、或另一次运行。

**运行**：任务在一个运行器上的一次执行，从触发到结束，视为黑盒。运行直接、通过编排器逻辑、或通过改变工单追踪器或 Git 托管来触发后续运行。运行从不等待人类：它结束，随后人类对工单追踪器或 Git 托管的变更触发新运行。*避免*：session

**运行器**：运行在其上执行的一次性机器。运行期间的任何东西都不会保留，即使机器本身长期运行：运行对早期运行的唯一记忆是工单追踪器、Git 托管和编排器。*避免*：server、host、box、compute、sandbox

## 服务

**工单追踪器**：工单所在之处，也是工厂的人机界面：人类通过提交工单安排工作、在评论中与代理对话，他们对工单的变更触发运行。*避免*：issue tracker、ticket manager、project board

**工单来源**：工厂外部、在工单追踪器中创建工单的任何东西：反馈按钮、监控器、错误追踪器、收件箱。*避免*：data source、trigger source、intake

**Git 托管**：分支、PR 和审查所在之处。*避免*：code host、forge、repo

**编排器**：接收触发器、在运行器上启动运行、记录哪些运行排队中、进行中或已完成的组件。*避免*：dispatcher、scheduler、control plane

**可观测性平台**：运行器发送日志、追踪和状态的地方，以便人类查看每次运行内部发生了什么。可选：填充运行器或编排器槽位的产品往往自带足够信息。运行从不基于它做决定，直到有东西将其写入工单追踪器或 Git 托管。*避免*：observability、logs、monitoring、dashboard

## 设计工厂

设计分两半：**服务**，每个是一个由产品填充的槽位；以及**任务**，其运行推动工作流经它们。

从用户的问题出发，而非工厂：未分拣的工单、等待自动审查的 PR、要迁移的更严格自动检查、没人读的 Bug。当用户提出问题或不知构建什么时，阅读 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md) 了解解决常见问题的任务。

### 起步要慢

每个触发器都是加速器。无刹车的加速器造出垃圾炮。有三种刹车：

* **自动检查**：每次运行必须通过的确定性关卡（类型、lint、测试）。
* **自动审查**：一个独立运行，冷读取 diff，对照代码库标准和工单（如果有）。
* **人工审查**：人类在合并前阅读 PR；发现的问题变成新的自动检查和更敏锐的自动审查。

一次加一个自动触发器，起初限流（十个 Bug 报告取一、时钟一天一次），每个 PR 都有人工审查。随刹车赢得信任再放宽限流，并将每个运行循环限制在人工介入前的几次尝试。

### 填满每个槽位

每个服务是一个槽位。一个产品可填多个槽位，一台服务器可托管多个服务。三种设计并列：

| 服务     | 全在 GitHub                       | Linear 工单                 | 自有追踪器    |
| ------ | ------------------------------- | ------------------------- | -------- |
| 工单追踪器  | GitHub Issues                   | Linear                    | 自有应用     |
| 工单来源   | 反馈按钮                            | 反馈按钮、监控器                  | 反馈按钮、监控器 |
| Git 托管 | GitHub                          | GitHub                    | GitHub   |
| 编排器    | GitHub Actions                  | 自有服务器 + 数据库               | 自有应用     |
| 运行器    | Actions 运行器                     | Actions、E2B、Daytona 或 VPS | 自有应用、或沙箱 |
| 可观测性平台 | none: Actions run pages suffice | 一个 LLM 追踪平台               | 自有应用     |

当用户为槽位选产品时，先读该槽位的调研以建立认知，再自行调研当前选项；每份调研按类型分组选项，并列出决定该槽位的问题：

* [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
* [GIT-HOSTS.md](GIT-HOSTS.md)
* [RUNNERS.md](RUNNERS.md)
* [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

买服务、造任务：任务承载用户设计，服务是通用的。偏好现成的工单追踪器：它健壮、大家已熟悉、外部用户易接入。

### 质疑每个任务

对每个任务，回答：

1. 什么触发它？
2. 它做什么，读写哪些服务？
3. 它接下来触发什么？
4. 人类在哪里重新介入？
5. 什么阻止两次运行做重复工作？

对每个工单来源，回答：什么阻止它提交同一个工单两次？

当每个槽位都指定了产品（可观测性平台除外，它可以是刻意的 none），且每个任务和工单来源对每个问题都有答案时，设计即告完成。
