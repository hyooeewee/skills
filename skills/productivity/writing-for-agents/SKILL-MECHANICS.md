# 技能机制

`writing-for-agents` 的特定分支：当文档是技能时会发生什么变化（frontmatter、调用选择和路由技能）。关于编写它的其他所有内容是 `SKILL.md` 中的通用参考。

## 调用

两种选择，权衡两种负载：

* 一个**模型调用型**技能保留了一个 `description`，以便代理可以自主触发它，其他技能也可以访问它。你仍然可以输入它的名称：模型调用*总是包含*用户访问；description 只会添加代理发现，而永远不会移除人类的访问。description 是技能的最高级上下文指针，强制一直保持加载状态：以永久上下文加载换取可发现性。内容全为引用的模型调用型技能也是共享引用的一个场所：另一个技能可以调用它，因此多个技能需要的引用集中在一个地方。机制：省略 `disable-model-invocation`，并编写一个面向模型的 description，包含触发分支（`SKILL.md` 中的指针编写规则完全适用）。
* 一个**用户调用型**技能移除了代理对 description 的访问权限：只有输入其名称的人类才能调用它，其他任何技能都无法调用。零上下文加载，但会消耗认知负载：你是必须记住它存在的索引。机制：设置 `disable-model-invocation: true`；`description` 变得面向人类：一行摘要，触发列表被剥离。

仅当代理必须自行访问该技能，或另一个技能必须访问它时，才选择模型调用。如果它只能通过手动触发，则将其设为用户调用，且无需付出上下文加载成本。

两个用户调用型技能都需要共享引用，但都无法存放：因为没有 description，两者都无法触发对方。将其推送到技能系统之外的普通文件中：任何技能都可以指向的外部引用。

## 按调用方式拆分

拆分时的调用分割（序列分割位于 `SKILL.md` 中）：当你有一个独特的首词应该单独触发它（你在提示中实际使用的触发词），或者另一个技能必须访问它时，拆分出一个模型调用型技能。你为新的始终加载的 description 支付上下文加载成本，因此独立访问必须值得。

## 路由技能

当用户调用型技能多到你记不住时，可以通过**路由技能**来治愈这种累积的认知负载：一个用户调用型技能，列出其他技能以及何时使用它们，这样人类只需记住一个技能，而不是许多个。它只能提示，无法触发它们：用户调用型技能没有 description，因此除人类之外任何人都无法访问它们。
