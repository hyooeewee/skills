## 它做什么

`grilling` 是访谈循环，它在任何人采取行动之前对计划、决策或想法进行压力测试。它将主体映射为一个**设计树**：每个决策都分叉成附着在其上的决策，并通过逐分支的方式对你进行访谈，直到没有任何假设被静默地保留下来。

它不会一次问一个问题，也不会一次问完所有问题。每一**轮**都会询问整个**前沿**：即所有前提条件已经确定的决策，除此之外别无其他。如果一个问题依赖于另一个问题，它们绝不会出现在同一轮中；一个取决于尚未确定答案的问题属于后续轮次。你的回答会确定决策，前沿向外推进，下一轮会询问那些被打通的问题。通常情况下，13 个问题会分布在约 3 轮中，而不是 13 轮。

## 何时使用它

输入 `/grilling`，或者当任务合适时，[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自动使用它。它是 grilling 家族中唯一由模型调用的 [skill](https://www.aihero.dev/ai-coding-dictionary/skill)，这就是为什么你很少亲自输入它：通常是你*确实*输入的某个技能在为你运行它。

直接输入 `/grilling` 只会得到普通的访谈，没有其他内容。当你需要更多时：

## 轮次、前沿，以及由谁决定

三个概念支撑着整个技能。

**设计树**是主体的模型：带有附着其上的决策的决策。**前沿**是所有前提条件都已确定的决策集合：是此时此刻唯一可以诚实询问的问题。**一轮**就是一次前沿，被完整询问并完整回答。

在一轮中，每个问题都以固定的形式出现：在 `❓` 后面编号并加标题，然后是正文，最后是 agent 单独给出的推荐答案，放在 `➡️` 行上。这就是为什么一轮可以按数字回答（“1 是，2 第二个选项，3 否，理由如下”）而不是通过引用问题来回答的原因。该格式有一个已知的粗糙之处：推荐答案有时会*反驳*问题本身的措辞，因此同意推荐答案意味着对该问题回答“否”。当发生这种情况时，请回答推荐答案并说明这一点。

设计的另一半是事实与决策的划分。事实是技能自己的工作：当前沿问题需要 [环境](https://www.aihero.dev/ai-coding-dictionary/environment) 可以确定的东西时，它会派遣 [子代理](https://www.aihero.dev/ai-coding-dictionary/subagent) 去查明，而不是问你。它不会在此阻塞；只有正在进行的探索下游的问题才会等待。决策是你的，它必须等待它们。一个运行 `grilling` 并自己回答决策的 agent 破坏了技能，而不是自由地解释它。当前沿为空时会话结束，在你确认已达成共同理解之前，它不会根据你达成的协议采取行动。

诚实的局限：前沿是 agent 的判断，而不是计算出来的图。它可能把两个问题放在同一轮中，之后才发现一个答案本应改变另一个。除了告诉它之外，没有其他防护手段，这会在下一轮重新打开受影响的支线。

## 常见问题

**我可以回到一次只问一个问题吗？**
可以，而且很大一部分用户都是这样做的。请将以下内容添加到你的全局 `CLAUDE.md`：

```
When grilling, ask one question at a time.
```

基于轮次的默认方式确实存在争议。阅读速度较慢、使用第二语言工作、或者将顺序格式作为专注支架的实践者都报告说，一次一个的节奏对他们更好，而且这种退出机制是得到支持的，而不是被容忍的。

`/batch-grill-me` 去哪了？进入这个技能。基于轮次的提问曾作为单独的技能短暂发布，然后移入了 `grilling` 本身，因此所有基于原语（`grill-me`、`grill-with-docs`、`triage`、`wayfinder`）构建的东西都立刻获得了它。没有 `batch-grill-me` 可安装，也没有单独的顺序技能；上面的 `CLAUDE.md` 行是回到一次一个问题的途径。

一次性问完一轮必然会失去我之前的回答本应引发的问题。不是吗？这是对轮次设计最常见的反对意见，而前沿就是对它的回答：一轮永远只包含不相互依赖的问题，因此一轮中的任何答案都不能使同一轮中的另一个问题无效。答案仍然会重塑所有下游内容：下一轮是重新计算的，而不是预先写好的。你失去的比“一次性问完所有问题”暗示的要少，也比什么都没有多：请参阅上面关于前沿限制的说明。

它问完了所有问题并开始构建。确认门正是为此而存在的：当前沿为空时技能并未结束，只有当你说理解已共享时才结束。较弱和较快的 [模型](https://www.aihero.dev/ai-coding-dictionary/model) 仍然会破坏它；这在对效率要求较低或非前沿模型上报告得最多，它们将“访谈直到达成共同理解”简化为几个问题和大纲。如果你的模型是这样，可靠的修复方法是在你自己的 `AGENTS.md` 或 `CLAUDE.md` 中加一行，告诉 agent 不要在未经许可的情况下实施。

**它自己回答了问题，而不是问我。**
这是运行中的 bug，不是预期行为，也正是技能文本中将事实与决策分开的原因。它最常见于另一个技能在"解决这个工单"的框架内运行 `grilling` 时，因为周围的任务会被理解为继续推进的许可。同样的约束也是为什么没有异步模式：人们曾要求一种变体，能读取 GitHub issue 并发布一份整合的决策备忘录，但那是另一个技能，因为一场没有人回答的 grilling 会话产生的是 agent 的意见，而不是你的。

我可以限制问题的数量吗？不可以，而且人为设置上限是有意超出范围的。有些计划需要 3 个问题，有些需要 50 个；固定的上限要么会截断难办的情况，要么在简单的情况下显得武断。用自然语言引导是预期的控制方式：告诉它收尾，或者停下来接受目前的计划。如果会话运行时间很长，原因通常是范围太大了；把工作拆分，然后逐块进行 grilling。

**我只安装了 `grill-me`，但什么也没有发生。**
`grill-me` 是一个只有一行的技能，其全部内容就是"运行一次 `/grilling` 会话"，所以它也需要安装这个技能。`grill-with-docs` 也是如此，它另外还需要 [domain-modeling](https://aihero.dev/skills-domain-modeling)。安装全套可以避免这个问题；有选择地安装则意味着也需要安装原语。

`grill-with-docs` 运行了，但它从未加载 `grilling`。
这是一个真实且未修复的粗糙边缘问题，在 [harnesses](https://www.aihero.dev/ai-coding-dictionary/harness) 和模型中都有报告：一个命名了另一个技能的技能并不会可靠地导致该技能加载，而 `grill-with-docs` 命名了两个。线索是一个会话一次性问完了所有问题，却没有附带任何建议：那是模型即兴发挥进行访谈，而不是运行这个访谈。直接询问 agent 它是否加载了 `grilling` 和 `domain-modeling` 通常能恢复它。

## 如果它起作用了

* 一轮以编号列表的形式呈现，每个问题及其建议分别放在独立的 `➡️` 行中，你可以按编号回答整轮。
* 一轮中的任何问题都不需要同一轮中的另一个问题先被回答。
* 后续轮次会问第一轮无法问出的问题。
* 它会去查找事实（读取文件、派遣子代理），而不是问你它本可以查明的事情。
* 后台运行的研究不会让当前轮次停滞；只有依赖它的那些问题才需要等待。
* 它会在最后停下来，请你确认双方理解一致，而不是直接开始工作。
* 问题数量保持在高位，而轮次数量保持在低位。

## 它在系统中的位置

`grilling` 是一个**原语**，而不是你安排的一个步骤：它是访谈技巧的单一事实来源，放在一个地方，这样每个需要访谈的技能都会使用它，而不是自行发明。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 是它的两个用户调用入口，`grill-with-docs` 是主构建链开始的地方，位于 [to-spec](https://aihero.dev/skills-to-spec) 之前。[wayfinder](https://aihero.dev/skills-wayfinder) 运行它来解决决策单，[triage](https://aihero.dev/skills-triage) 用来把一个含糊的报告“拷问”成可操作的报告，而 [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 则在你选定一个候选方案深入后遍历树。当你不确定哪个入口合适时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你路由。
