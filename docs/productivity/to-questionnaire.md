## 它做什么

to-questionnaire 将一个你无法独自做出的决策转化为一份 **问卷**：一份 Markdown 文档，交给那个掌握你所缺失信息的人，让他们异步填写，或者你和他们在会议中一起讨论。

它盘问的是 **发送对象**，绝不涉及主题。针对主题的访谈毫无意义，因为正是不了解主题你才要写信给别人。所以它只问两件你总能回答的事（发给谁，以及你需要对方回馈什么），并让文档里的每个问题都瞄准这两者之间的 **差距**。

## 何时使用它

你通过输入 `/to-questionnaire` 来调用它；[代理](https://www.aihero.dev/ai-coding-dictionary/agent) 不会主动使用它。

当某个决策因只有另一个人脑子里有的知识而卡住时，就用它：客户、领域专家、掌握业务规则的高管、不在你团队的同事。你想要哪个技能，取决于答案在哪里：

| 答案在……              | 选择                                                           |
| ------------------ | ------------------------------------------------------------ |
| 你自己脑中，但尚未厘清        | [grill-me](https://aihero.dev/skills-grill-me)               |
| 代码库中               | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑中              | `to-questionnaire`                                           |
| 尚无人在脑中，问题需要某种反应对象。 | [prototype](https://aihero.dev/skills-prototype)             |

常见情况是一次 [盘问](https://www.aihero.dev/ai-coding-dictionary/grilling) 会话陷入停滞，因为它提出的一些问题不是你能回答的。在同一个对话中运行 `/to-questionnaire`，把那些问题转为线下处理，然后把答案带回来继续推进。

## 发送对象，而非主题

这场访谈只有两轮对话，然后就不再问了。

* **发给谁？** 对方的角色、专长、与你的关系。这决定了文档的语气和必须携带的上下文量。外部客户需要背景铺垫；队友则不需要。
* **你需要回馈什么？** 那些你独自无法拍板的具体决策或事实。这会变成成品文档的核对清单。你列出的每一项，都会得到一个针对它的问题。

之后全是起草。技能把文件写到当前目录下的 `to-questionnaire-<slug>.md`。无需设置、无需工作区、无需任何配置。

## 文档

这份文档是一份 **发现型问卷**，因为你缺上下文，而收件人有。这决定了它的结构：

* 一行目的，点明依赖于它的决策；一段简短背景，给完全不了解你来龙去脉的收件人看。
* 问题按**最重要者优先**排序，并按主题分组，因为异步意味着你可能只有一次机会。
* 每个问题只讲一件事，绝不复合，下方留有作答区；只有在问题可能被误解时，才加上一行 *为什么这很重要*。
* 明确允许回答 „我不知道“，因为被标记的不确定性是有用的，而读起来像事实的自信猜测则没有用。
* 一个结尾兜底问题：有没有我们没问到、但我们应该知道的事情？

文档刻意不做两件事。它不是 **分支式** 的。问题扁平分组，不是答了 A 就跳过 D 的树。它也不是 **多收件人** 的。一次运行产出一份文档，给一个人。

## 常见问题

**它会读取我的盘问会话并提取问题吗？** 不会，这不是它的一个步骤。技能没有摄入阶段。它问发送对象，然后起草。之所以在盘问会话后能生效，是因为你在 **同一个对话** 里运行它，所以 [会话](https://www.aihero.dev/ai-coding-dictionary/session) 已经在 [上下文](https://www.aihero.dev/ai-coding-dictionary/context) 里，起草时可以直接引用。如果你在新会话里启动它，它对盘问一无所知，当你回答 „你需要回馈什么“时，得自己再把主题说一遍。

**缺失的答案不都在同一个人手里。能按收件人拆分吗？** 不能。第一步就询问 *那个* 收件人，单数，整份文档的语气和上下文都针对那个人。如果三个人各掌握一部分答案，就运行三次，每人一次。有人想要一份文档、按学科或角色路由问题，但该功能未上线。

**问题有依赖关系吗：会根据前面的答案跳过章节吗？** 不会。依赖式问题设计探索过但未上线。输出是静态文档：主题分组、最重要优先、每个问题都有效。反对意见是公平的。一个 [模型](https://www.aihero.dev/ai-coding-dictionary/model) 如果在真实答案到来前规划超过两三个问题，规划得就很烂；而分支式文档必须在每个答案前把所有问题都规划好。

**收件人也不知道怎么办？** 文档会告诉他们说出来。它明确要求 „我不知道“ 和部分回答。一个被标记的不确定性比猜测更有价值，因为模糊的回答和自信的错误回答一旦回到你的上下文里看起来一模一样。

**它会发到别处吗（Slack、工单系统、邮件）？** 不会。它在当前目录写一个 Markdown 文件并告诉你路径。投递由你决定：贴进 [工单](https://www.aihero.dev/ai-coding-dictionary/ticket)、扔进 Slack 线程、作为邮件附件、或者在共享屏幕上打开现场填。这四种人们都手动做过。

**这不就是 `/grill-me` 的批处理模式吗？** 不是。`grill-me` 本来就按 **轮次** 提问。它一次性问出所有开放问题的前沿，然后根据你的答案重新计算，所以早已满足 „一次性给我所有问题“ 的需求。`to-questionnaire` 区别在于另一个维度：它关注答案在谁脑子里，而不是问题怎么送达。想自己更快答完，用 `grill-me`。想从别人脑子里把答案取出来，用这个。

**不用技能、直接让代理干不行吗？** 行，且在技能出现前很多人这么干过：`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、每个未答问题开一个 „需要更多信息“ 工单。技能给你买到两点：访谈永不偏向主题，且产出的文档非技术收件人也能直接填。如果你已有成熟的内部格式，就不需要这个。

## 如果它起作用了

* 它问收件人、问你需要回馈什么，然后就不问了。如果它问起主题本身，说明技能出错了。
* 你列为“我需要回馈什么”的每一项，都可以在文件中追踪到对应的问题。
* 问题读起来是针对*收件人*所知道的，而不是把你自己的未解决问题逐字照抄下来。
* 你可以把文件递给一个没有参与对话的人，对方会明白自己为什么收到它，以及应在什么时候之前回复。
* 收回来的答案可以作为新一轮盘问的有效输入，而不是又一组新问题。

## 它在系统中的位置

`to-questionnaire` 是随时可用的独立技能。你在自己的知识到头、下一步是问别人而不是跑另一个技能时用它。这最常发生在流程中段，规划因非你所能决策的事卡住时。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者的区别在于答案在谁那里。盘问从你那里取答案；问卷从别人那里取。把回来的答案喂进下一轮盘问，或喂进 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)（如果工作要走向构建）。不确定哪个技能适合当下时，[ask-matt](https://aihero.dev/skills-ask-matt) 会把你导向正确的方向。
