## 功能说明

`to-questionnaire` 将一个你自己无法决定的决定转化为一个**问卷**——一份 Markdown 文档，你把它交给那个掌握你所缺失信息的人，让他们异步填写，或者你们两人一起在会议上讨论解决。

它只会就“发送对象”进行盘问，绝不会涉及话题本身。在这里，就话题采访你毫无意义：不知道话题正是你要写信给别人的原因。因此，它会询问那两个你总能回答的问题——发给谁，以及你需要从中得到什么——并将文档中的每个问题都针对这两者之间的**差距**。

## 何时使用

You invoke this by typing `/to-questionnaire` — the [agent](https://www.aihero.dev/ai-coding-dictionary/agent) won't reach for it on its own.

当某个决定因存在于另一个人脑中的知识而被阻碍时，使用它：客户、领域专家、拥有业务规则的执行层、你不坐在一起的那个团队的同事。你想使用哪个技能取决于答案实际上在哪里：

| 答案在……                    | 使用                                                           |
| ------------------------ | ------------------------------------------------------------ |
| 你自己的脑海，未打磨               | [grill-me](https://aihero.dev/skills-grill-me)               |
| 代码库                      | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑海                    | `to-questionnaire`                                           |
| 还没人在脑海中有答案——这个问题需要某种反应对象 | [prototype](https://aihero.dev/skills-prototype)             |

常见的情况是一个陷入停滞的[盘问](https://www.aihero.dev/ai-coding-dictionary/grilling)会话： surfaced 出来的一些问题不是你的答案。在该会话中运行 `/to-questionnaire` 将这些问题离线处理，然后带回答案并继续。

## 发送对象，而非话题

采访只有两次交流，然后就会停止。

* **发给谁？** 他们的角色、他们的专长、他们与你的关系。这决定了文档的基调以及它需要承载多少背景信息——外部客户需要引导，而队友则不需要。
* **你需要得到什么？** 你独自无法解决的 concrete decisions 或 facts。这成为了衡量最终文档的检查清单：你命名的每一项都会得到一个针对它的提问。

此后的一切都是起草工作。文件会落在当前目录下的 `to-questionnaire-<slug>.md`。没有设置，没有工作区，也没有需要配置的东西。

## 文档

It is framed as a **discovery questionnaire** — you lack the context, the recipient holds it — and that framing drives its shape:

* 一个指明其承载的决策的目的行，以及为从未进入你脑海的接收者提供的简短背景部分。
* 问题按**最重要在前**排序并归类在主题标题下，因为异步意味着你可能只能有一次机会。
* 每个问题一个想法，绝不复杂化，下方有一个回答占位符，并且只有在问题可能被误读的地方才有一行*为什么这很重要*。
* 明确允许回答“我不知道”——标记出的不确定性是有用的；读起来像事实的自信猜测则没有用。
* 一个结尾的兜底：有什么我们没有问但我们应该知道的吗？

它刻意不包含的两件事。它不是**分支式**的——问题是一个扁平的分组列表，而不是如果你回答了 A 就跳过 D 部分的树状结构。它也不是**多接收者**的——一次运行只生成一个针对一个人的文档。

## 常见问题

**它会读取我的盘问会话并从中提取问题吗？**
不是作为一个独立的步骤。该技能没有摄取阶段：它先询问发送对象，然后起草。在盘问会话后它之所以有效，是因为你在**同一个会话**中运行它，因此[会话](https://www.aihero.dev/ai-coding-dictionary/session)已经处于[上下文](https://www.aihero.dev/ai-coding-dictionary/context)中，起草工作可以从中汲取养分。在新的会话中启动它，它对盘问一无所知——当你回答“你需要得到什么？”时，你会自己重新提供话题。

**缺失的答案并不都存在于同一个人的脑海中。它可以按接收者进行拆分吗？**
不行。第一步要求的是*那位*接收者（单数），整个文档的基调和背景都是针对他们的。如果三个人分别持有答案的三个部分，就运行三次，每人一次。在单个文档中按学科或角色路由问题是一个人们提出的要求；但已发布的功能并不包含这一点。

**问题是相互依赖的吗——它会根据之前的答案跳过某些部分吗？**
不会。相互依赖问题的设计被探讨过，但并未发布。输出是一个静态文档：主题分组，最重要在前，每个问题都存在。反对它的理由是合理的——一个[模型](https://www.aihero.dev/ai-coding-dictionary/model)在真实答案之前规划超过两三个问题会规划得很差，而分支式文档必须在每个答案之前规划好所有问题。

**如果接收者也不知道怎么办？**
文档告诉他们这么说。明确要求“我不知道”和部分答案，并且标记出的不确定性比猜测更有价值，因为一旦回到你的上下文中，模糊的答案和自信的错误答案看起来一模一样。

**它会发送到任何地方——Slack、问题跟踪器、电子邮件？**
不会。它会在当前目录下写入一个 Markdown 文件并告诉你路径。发送由你负责：粘贴到[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)中，放入 Slack 线程中，附加到电子邮件，或在共享屏幕上打开并实时处理。人们已经手动实现了所有这四种方式。

**这不就是 `/grill-me` 的批处理模式吗？**
不是，而且这个区别值得保留。`grill-me` 已经以**轮次**形式提问——一次性提出整个前沿，然后根据你的答案重新计算——所以“一次性给我所有问题”的需求在那里得到了满足。`to-questionnaire` 涉及的是不同的维度：不是问题如何交付，而是答案在谁的脑海中。你自己更快地回答它们是 `grill-me`；从别人那里获取它们是这个工具的用途。

**难道我不能直接问 agent 而不使用这个技能吗？**
可以，在它存在之前很多人都这么做——`OPEN_QUESTIONS.md` 文件，发送给客户的电子表格，每个未回答问题对应一个“需要更多信息”的工单。该技能为你带来两件事：采访绝不会偏离话题，而且文档会以非技术接收者可以实际填写的形式呈现。如果你已经有一个行之有效的标准格式，诚实的答案是：你不需要这个。

## 判断是否生效

* 它询问接收者以及你需要得到什么，然后停止提问。关于话题本身的问题是该技能跑偏的标志。
* 你命名的每一项“我需要得到什么”都能追溯到文件中的一个问题。
* 问题读起来像是针对*接收者*所知道的，而不是你自己的开放式问题逐字照抄下来的。
* 你可以把文件交给一个不在对话中的人，他们会知道为什么要给他们以及什么时候回复。
* 返回的答案是新一轮盘问的有用输入，而不是一组新问题。

## 在系统中的位置

`to-questionnaire` 是一个随时可以使用的独立工具。它位于你自己知识的边界，下一步是另一个人而不是另一个技能——通常是在流程中途，当规划因某件不属于你决定的事情而停滞时。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者在答案所在之处分道扬镳：盘问从你身上挖掘，问卷从别人身上挖掘。返回的是原材料——将其投入新一轮盘问，或者如果工作走向构建，则投入 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。当你不确定哪个技能适合此时此刻时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你指引。
