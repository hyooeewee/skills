## 它做什么

`tdd` 以测试优先的方式构建功能或修复 bug：一个失败的测试，然后是刚好足够的代码让它通过，然后是下一个行为。它承载着使该循环产生值得保留的测试的标准：什么是好的测试，测试放在哪里，mock 是用来做什么的，以及那三个悄无声息地破坏测试套件的反模式。

它不会在你尚未预先同意的接缝处写任何测试。在任何测试存在之前，它会列出它打算测试的公共边界，并停下来等待你的确认，因为测试精力是有限的，而这里正是你把精力花在关键路径上而不是每个边缘案例上的地方。另外需要知道的是，`tdd` 是一个**参考**，而不是驱动者。它持有这个循环的规则，而由其他东西（你，或 [implement](https://aihero.dev/skills-implement)）来运行应用这些规则的[会话](https://www.aihero.dev/ai-coding-dictionary/session)。

## 何时使用它

输入 `/tdd`，或者当任务符合条件时，[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自动使用它：以测试优先的方式构建特性或修复 bug，或者当你说了“red-green-refactor”时。

当有一个具体的行为要构建——有输入和可观察的输出——并且你希望测试能在重构后依然有效时，就使用它。

| 你的情况                                                                                                                                      | 去哪里                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 具有明确定义输入和输出的行为（业务逻辑、请求/响应契约、转换、验证）                                                                                                        | `tdd`                                                            |
| 行为尚未确定                                                                                                                                    | [to-spec](https://aihero.dev/skills-to-spec)，它也会在任何代码编写之前约定好测试接缝 |
| 真正的问题在于接口的形状，而不是测试                                                                                                                        | [codebase-design](https://aihero.dev/skills-codebase-design)     |
| 你有一个 [规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)或 [工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，并且希望整个构建流程由代理替你运行 | [implement](https://aihero.dev/skills-implement)，它驱动 `tdd`按工单    |
| 配置、接线、胶水代码、类型注解、直接的 CRUD 委托                                                                                                               | 这里没有合适的选项；请参阅下方的开放缺口                                             |

最后一行是一个真正的缺口，而非风格偏好。该技能决定*在哪里*放置接缝；其中没有任何东西决定*是否*值得进行这个循环。如果在一个没有独立真相来源可供断言的变更上运行它，你会得到一个重述实现的测试：这是技能本身警告的同义反复反模式，是从另一个方向达成的。这是 [issue #746](https://github.com/mattpocock/skills/issues/746)，目前是开放的。在它关闭之前，那个判断权属于你或你的 `CLAUDE.md`。

## 先决条件

需要安装 [codebase-design](https://aihero.dev/skills-codebase-design)。`tdd` 以前自带深模块和接口设计笔记；在 v1.0 中，为了支持共享技能，这些被删除了，`tdd` 现在依靠它来获取接口设计词汇。没有其他内容；该技能是 [无状态](https://www.aihero.dev/ai-coding-dictionary/stateless) 的，并且不写自己的文件。

## 这个循环，以及它所运行的接缝

三个词承载着这个技能。

**红-绿。** 先写失败的测试，然后只写足够让它通过的代码。不要提前预想尚未写到的测试。没有重构阶段：它在 2026 年 6 月被移除，因为代理基本上从不执行它，也因为审查和实现分开在不同会话中效果更好。重构属于 [code-review](https://aihero.dev/skills-code-review)。

**垂直切片。** 一个接缝、一个测试、一个最小实现，然后重复，第一个周期是一个**曳光弹**，证明了单一路径端到端。相反的是水平切片：先写所有测试，再写所有代码。批量测试验证的是*想象中*的行为，它们检查的是事物的形状，而不是用户做了什么，它们在你理解实现之前就让你承诺了一个测试结构。

**预先约定的接缝。** 接缝是你观察行为的公共边界，而无需深入其中。规则是绝对的：在未确认的接缝上没有测试。在完整链路中，接缝在 [to-spec](https://aihero.dev/skills-to-spec) 期间更早地达成一致：`"/tdd"` 被告知只能在工作于预先约定的测试接缝上，`"/code-review"` 检查是否只使用了商定的测试接缝。单独调用时，`tdd` 会直接问你。

它被编写出来要防止的三种反模式：

| 反模式  | 识别特征                                                                |
| ---- | ------------------------------------------------------------------- |
| 实现耦合 | 当你重命名一个内部函数时测试就会失败，尽管行为并没有改变。比如 mock 了内部协作者、断言调用次数、用数据库查询而不是用接口来验证。 |
| 同义反复 | 期望值是按照代码计算它的方式来计算的，因此测试通过是必然的。期望值必须来自别处：已知良好的字面量、一个已解决的示例、或者规格说明。   |
| 水平切片 | 一批测试在任何实现之前就落地了。                                                    |

Mock 只用于系统边界：外部 API、时间、随机性，有时是文件系统或数据库。不是你自己的模块。

## 常见问题

**为什么它不重构？描述里明明写着“红-绿-重构”。**

因为重构步骤被移除了，而描述没有更新。移除是经过深思熟虑的：代理基本上从不执行它，而且把实现和审查分开在不同会话中效果更好。结果是否还算得上正统的 TDD，没有这个循环是否能产生更好的代码重要。触发短语和正文之间的不匹配被记录为 [issue #589](https://github.com/mattpocock/skills/issues/589)，目前仍然开放，所以“红-绿-重构”仍然可以作为触发该技能的短语。你得到的是红 → 绿，而重构在 [code-review](https://aihero.dev/skills-code-review) 中完成。

**它让我选择一个测试接缝，而我完全不知道选哪个。**

这是该技能报告最多的摩擦点之一（[issue #607](https://github.com/mattpocock/skills/issues/607)）。提示只按名称列出候选接缝，没有关于每个接缝捕获或遗漏了什么的说明，所以你是在标签之间做选择。目前还没有已发布的修复方案。实用的变通方法是先询问代理权衡取舍：组件级接缝遗漏了什么集成接缝捕获了，以及它慢多少。这也是为什么链路会在 `to-spec` 中提前商定接缝，在那里你可以看到整个功能，而不是一个提示。

**它先写了实现再写测试，尽管技能说的是先红。**

这种情况会发生。一位用户向 [模型](https://www.aihero.dev/ai-coding-dictionary/model) 施压，得到了一个异常诚实的回答：“我知道技能说了‘一次一个测试，观察它以正确的原因失败’。我读了。我只是默认了我的正常习惯。”该技能是设计来容忍这种情况的。没有指令能让代理 100% 地遵守，而且强行强调只会以微小的收益限制代理的创造力；即使不严格遵循，循环也值得运行，因为结果仍然更好。如果对特定的切片严格遵循很重要，请观察运行过程，而不是信任技能来强制执行它。

**它应该先写浏览器测试或端到端测试吗？**

通常不应该，而且这个技能也不会阻止它。一位用户报告说，代理先写了 Playwright 测试，然后烧掉一个很长的循环反复运行它，最终得出结论说*测试*坏了——而那个功能根本还不存在。请在你的 `CLAUDE.md` 中配置这一点。浏览器测试足够慢，红-绿反馈循环不再划算；请在仓库的 `CLAUDE.md` 中声明这些测试应该在行为正常工作之后再写。

**&#x20;`/tdd`是否会取代 `/implement`，或者是课程中的 `/do-work`？**

不。`/tdd` 记录的是方法论；`/implement` 是一个非常简单的工作→反馈→提交循环，是 `/do-work` 的直接替代品。课程中单一的 `/do-work` 步骤现在被拆分到了 `/implement`、`/tdd` 和 `/code-review` 中。如果你在问针对某个工单应该运行哪一个，答案几乎总是 `/implement`。

**深度模块和接口设计的指南去哪里了？**

在 v1.0 中并入 [codebase-design](https://aihero.dev/skills-codebase-design)，经过泛化，使多个技能共享一套词汇。`refactoring.md` 同时被移除；重构现在由 [code-review](https://aihero.dev/skills-code-review) 负责，该技能承载了 Fowler 的坏味道基线。

**它知道我其他的工单吗？**

不知道。针对一个工单运行时，它会很乐意提议属于兄弟工单的工作，因为它看不到问题图的其余部分（[issue #129](https://github.com/mattpocock/skills/issues/129)）。Matt 的立场是这不是 `tdd` 的职责。将规格说明与工单一起传入会有所帮助；从一开始就把工单的粒度定合适则更有帮助。

## 如果它起作用了

* 它会停下来，说出它打算测试的接缝，然后在任何测试文件存在之前等待。
* 一个测试出现，变红，获得刚好足够的代码让它通过，然后只有这时下一个测试才出现，而不是先有一批测试再有一批代码。
* 测试名称读起来像能力（“user can checkout with valid cart”），而不是内部实现（“checkout calls paymentService.process”）。
* 断言中的期望值是你能追溯到规格说明的字面量，而不是像代码那样重新计算出来的值。
* 重命名一个内部函数不会破坏测试套件中的任何东西。
* Mock 只出现在外部边界（支付 API、时钟）周围，绝不在你自己的模块周围。

## 它在系统中的位置

`tdd` 是主链路中构建步骤内部的引擎，而不是独立的一步：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

[to-spec](https://aihero.dev/skills-to-spec) 提前商定测试接缝，[implement](https://aihero.dev/skills-implement) 按工单驱动 `tdd`，而 [code-review](https://aihero.dev/skills-code-review) 随后检查是否只使用了商定的接缝，并拥有 `tdd` 不再执行的重构。它的另一个邻居是 [codebase-design](https://aihero.dev/skills-codebase-design)，这是 `tdd` 所说的接缝和深模块词汇的共享来源。你也可以随时单独使用它，只要有具体的行为要构建且没有完整的规格在运行。当你不确定哪个技能适合你的情况时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你路由。
