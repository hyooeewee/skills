## 它做什么

`prototype` 编写 **一次性代码来回答一个问题**：这个状态模型感觉对吗，或者这个屏幕应该是什么样子的。问题优先，并决定了后面所有事物的形态；一个回答了错误问题的原型尽管看起来再好也是纯粹的浪费。

一次性是一种对代码*编写方式*的约束，而不是销毁它的承诺。没有测试，没有能让它跑起来的错误处理之外的东西，没有抽象，没有持久化，因为这些东西都不能帮你学习你正试图学习的唯一一件事。幸存下来的是答案，它被折叠进真实代码中，原型本身则作为一个分支上的证据，证明答案来源于此。

## 何时使用它

输入 `/prototype`，或者当任务合适时，[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 会自动使用它。

一旦遇到一个无法通过交谈确定的问题，就立刻使用它：一个边缘情况多到你无法记在脑海中的状态机，一个只有看到三个版本并排时才能想象出的屏幕。[拷问](https://www.aihero.dev/ai-coding-dictionary/grilling) 会话正是因这些问题而膨胀：agent 重新表述，你猜测，范围随之扩大以填补不确定性。停止拷问，构建一次性版本，查看它，然后用一句话回答。如果相反，一个已构建的东西表现异常而你想知道原因，请使用 [诊断 bug](https://aihero.dev/skills-diagnosing-bugs)；原型探索的是要构建什么，而不是已构建的东西为何坏掉。

你也会在不经意间来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 在其地图上归档 `prototype` 决策 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)，处理其中一个 ticket 就是本技能。

## 两个分支

问题决定分支，而各个分支产生截然不同的产物：

* **“这个逻辑/状态模型感觉对吗？”**：一个**可分享的单个 HTML 文件**。一个独立的页面，不需要构建和服务器，通过双击打开。它包含一个标记了的状态面板，每次点击后重新渲染，有自由按钮可以按任意顺序测试模型，以及带标签的**引导式演练**（每个标签页一个场景，每个场景下面都有需要按下的有序按钮）。所有内容都用领域语言标记，所以你可以把它交给设计师、产品经理或领域专家，让他们自己去感受模型。页面背后的逻辑是一个小的纯模块（reducer、机器、一组函数），保持与 DOM 分离，这样验证后的版本可以直接升入真实代码。
* **“这应该是什么样子的？”**：一个路由上的几种**截然不同**的 UI 变体，可以通过浮动底部栏和 `?variant=` URL 参数进行切换。变体必须在结构上不一致，而不仅仅是颜色上；三个微调过的卡片网格只是壁纸，不是原型。它们尽可能在真实页面中渲染，使用真实数据和真实密度，因为在真空中判断的变体总是看起来不错的。

两者都保持状态在内存中，无需思考即可开始，并在每一步后显示完整状态。一旦发现自己正在固化其中一个（添加测试、连接真实数据库、为以后可能需要的案例进行泛化），你就停止了原型设计。

## 原型是一手来源

一个完成的原型留下两样东西，它们去向不同的地方。

**答案**（裁决加上它解决的问题）被持久化地捕获：提交信息、ADR、实现问题。这是 main 分支保留的内容，被折叠进真实代码中。

**原型**是答案的可运行证据，它不会被删除。它也不属于 main 分支：那里没有什么可维护的，而且它会很快腐烂。所以它被提交到一个从 main 分支出来的一次性 `prototype/<name>` 分支中，永不合并，并在实现问题上留下一个指向该分支的 [上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净；探索过程保持可被发现且可重运行，以便下一位接手工作的人可以继续。

## 常见问题

**等等，原型不应该被删除吗？** 不再这样了。以前是：构建它，保留答案，扔掉代码。对此最尖锐的反对意见从来不是关于速度：而是*下个 [会话](https://www.aihero.dev/ai-coding-dictionary/session) 谁来接手这项工作，以及他们有什么可工作的东西？* 原型的文字摘要丢失了让它令人信服的东西。所以原型现在被视为 [一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)：它落在 main 分支下的 `prototype/<name>` 分支上，实现问题指向它。改变的是代码所在的位置，而不是纪律；它仍然永远不会合并进 main 分支。

**它以前构建终端应用。那个去哪了？** 现在逻辑分支发出的是一个可分享的 HTML 文件。终端应用只能由克隆了仓库并安装了运行时的人驱动，这恰恰排除了原型所需要的意见的人：设计师、PM、知道状态模型应该意味着什么的领域专家。一个通过双击打开且能经受住邮件发送的独立文件可以由任何人驱动。下面的纯逻辑模块未变，仍然是升入真实代码的部分。

**有一个 agent 告诉我要 `/prototype`，而我当时应该在实现功能。**
已知问题，这是一个命名问题。`prototype` 是一个通用且吸引人的词，对于不了解流程的 agent 来说，一旦存在 tickets，它就会被理解为"显而易见的下一步"，所以即使设计已经在对话中完全确定，它也会被按名字推荐。如果你已经知道要构建什么，下一步就是按 ticket 执行 `/implement`。只有当某个具体的设计问题真正悬而未决且交谈无法解决时，才使用原型。

**我应该在构建任何生产功能之前（比如，为了向潜在客户演示）对整个应用做原型吗？** 这是另一个顶着这个技能名字的不同产物。这里的原型是针对一个问题的，而“整个应用是什么？”不是一个问题。全应用原型没有自然的停止点，所以它会凭借惯性变成生产应用：清理循环从未发生，在原型规则下编写的代码（无测试、无错误处理）最终呈现在用户面前。如果你需要销售演示，就明确地将其构建为演示，并说明其中没有任何生产内容。如果你需要解决一个设计问题，就把它缩减到那个问题。

**我如何在自己的会话中运行它？**
原型存在于自己的目录中，并产生大量你不想留在提问线程中的 [context](https://www.aihero.dev/ai-coding-dictionary/context)，所以在其他地方运行它，只带回答案。[handoff](https://aihero.dev/skills-handoff) 是双向的桥梁。

**这不是消耗 token 最快的方式吗？**
可能是的，如果你对本来可以通过交谈回答的问题做原型，或者让一个原型蔓延到整个功能。重要的比较不是 token 对零；而是 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) 对比构建了错误的状态模型然后在它有了生产调用者之后才发现。保持问题窄小、运行短暂，花费就会保持合理。

## 如果它起作用了

* 你可以用一句话说出原型存在的目的是回答什么问题，并且这写在了演示的顶部，而不只是在你的脑海里。
* 一个不读代码的人也能驱动逻辑演示。他们打开文件，在演练标签页中按下按钮，并用他们自己的话描述所见。
* 有人说"等等，那不应该可能"或"嗯，我以为 X"。这是*想法*中的 bug，而这正是全部意义所在。
* UI 变体在布局和信息层级上不一致，而不仅仅是颜色和文案，你得到的反馈是“来自 B 的头部和来自 C 的侧边栏”。
* 它在一口气之内得到回答。如果一天后你还在构建它，那问题太大了；把它拆开。
* 当它结束时，main 包含决策而不包含任何原型，实现 issue 指向仍然保存着它的分支。

## 它在系统中的位置

`prototype` 是一种**随时可用的独立技能**：你进入它以解决一个设计问题，然后退出来，它也是另一个技能运行的机器。

它最大的消费者是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 地图由**决策 tickets** 组成，而 `prototype` 是 ticket 的四种类型之一：当阻塞性的问题是"这应该看起来怎么样"或"这应该怎么表现"时使用它，这些问题再多的讨论也无法解决。wayfinder 通过创造具体可反应的东西来提高模糊讨论的保真度，而本技能就是构建那个具体东西的方法。一个原型 ticket 由答案解决，原型作为资产从地图上链接。

其他邻居位于其上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可拷问的问题；不可拷问的问题则来到此处，而一行答案会回到访谈中。下游，经过验证的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的既定输入，后者可以内嵌原型产生的富含决策的片段，而不是用散文描述。至于其他任何问题，[ask-matt](https://aihero.dev/skills-ask-matt) 会将你路由到整个集合。
