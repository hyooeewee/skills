## 它做什么

`research` 通过阅读拥有答案的来源来回答问题，然后在仓库中留下一个附带引用的 Markdown 文件。它仅从\*\*[主要来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)\*\*工作：官方文档、源代码、规范、第一方 API。它将每个声明追溯回其所属的来源，因此当 API 的官方文档可访问时，它不会重复博客文章对 API 的描述。

它不会在对话中回答你。输出是一个文件，写入仓库中已经存放此类笔记的位置，并在每项声明上附有链接。这正是关键所在：一份你可以回应、交给另一个代理、或丢弃的文档，而不是一个在[会话](https://www.aihero.dev/ai-coding-dictionary/session)结束时消失的答案。

## 何时使用它

输入 `/research`，或者当任务变成阅读性的跑腿工作时，[代理](https://www.aihero.dev/ai-coding-dictionary/agent)会自动使用它。

当下一步是*从工作目录外了解情况*（第三方 API 的行为方式、规范的实际内容、某个版本声明是否成立），而你又不想因为阅读而拖慢自己的线程时，请使用它。你需要什么决定了使用哪种技能：

| 你需要什么                            | 选择                                                           |
| -------------------------------- | ------------------------------------------------------------ |
| 决策所等待的一个外部事实                     | `research`                                                   |
| 一个通过访谈 *与你*共同做出的决定               | [追问](https://aihero.dev/skills-grilling)                     |
| 一个持久的架构决策，写入 `CONTEXT.md`和 ADR 中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 查明某种方法在你的代码库中是否可行                | [prototype](https://aihero.dev/skills-prototype)             |
| 一个在单次会话中装不下的庞大计划                 | [wayfinder](https://aihero.dev/skills-wayfinder)             |

`research` 和 `grill-with-docs` 之间的界限在于**返回内容的保质期**。研究产生的是短期资产：本周这个库的认证机制是如何工作的。ADR 记录的是你保留的决定。如果你正在产出的是一个决定而不是一个事实，那么你是在[追问](https://www.aihero.dev/ai-coding-dictionary/grilling)，而不是在进行研究。

## 委派的跑腿工作

关键的一步在于阅读作为**后台代理**运行。你继续工作；它去执行，将每个声明追踪到其主要来源，写入一个 Markdown 文件，然后汇报回来。研究是你委派的跑腿工作，而不是你外包的思考：你会得到一份文档用于追问、规划或设计，而你仍然做出最终决定。

这种委派没有设防，后台代理还可以再派生一个属于它自己的后台代理。这是该技能被记录得最充分的粗糙边缘。

文件落在哪里由仓库决定，而不是由技能决定：它会匹配仓库已有的任何笔记约定，如果没有，它会挑一个合理的地方并告诉你。每次运行只写一个文件。

## 常见问题

**它派生了一个第二研究代理。这是预期中的行为吗？**

不。这是一个开放中的 bug，[issue #530](https://github.com/mattpocock/skills/issues/530)。该技能告诉其调用者启动一个后台代理，但没有限制代理类型，因此它派生出的代理是一个 `general-purpose` 代理，它持有 `Agent` 工具和相同的指令，并再次触发它们。一位报告者测量到，在三次重叠运行中，单个研究任务大约消耗了 450k [tokens](https://www.aihero.dev/ai-coding-dictionary/token)，重复任务在半小时后完全不可见地完成了。这在 Claude Code 之外也能复现；在 Codex 中使用 GPT-5.6-sol 也确认了同样的嵌套现象。目前没有已发布的修复方案。用户通过在安装的副本中添加一行代码，指示一个已经是 [subagent](https://www.aihero.dev/ai-coding-dictionary/subagent) 的代理自行完成工作，这有所帮助，但只是指令层面的修复，而非结构性的修复。调用后请留意你的后台任务列表，并停止重复任务。

相反方向的失败同样存在：如果你自己的全局指令禁止代理重新委派工作，后台代理会礼貌地拒绝任务，而该技能会悄悄地什么都不做。

**文件应该放在哪里，我应该提交它吗？**

该技能将文件放在仓库已经存放笔记的地方，除此之外没有其他意见。社区的共识相当一致：保留 ADR，但不保留研究文件。来自 Discord 线程的最尖锐观点是：“ADR 是的。其他所有内容都在完成后归档或删除。否则它就会变成工作的垃圾，如果你偏离了规范/研究，还会毒害未来的仓库读取。”研究文件记录的是它被编写时的真实情况，因此过时的文件比没有文件更糟。总的来说，这些产物并不真的属于 git，也没有一个标准归宿：人们使用 Obsidian、独立的知识仓库或问题跟踪器。

**什么才算"高信任度"的主要来源，由谁来决定？**

[模型](https://www.aihero.dev/ai-coding-dictionary/model) 会做这件事。该技能命名了有资格的来源*类型*（官方文档、源代码、规范、第一方 API），没有允许列表、没有域名门槛，也没有验证关卡。这是该技能最初被提议时最大的反对意见，且从未得到公开回应：“五个研究子代理指向垃圾只会让你更快得到五个自信的错误答案。你如何控制什么算作高信任来源？”你实际拥有的缓解措施是每项声明上的引用。跟随其中两三个。如果它们落在对事物的总结上而不是事物本身，那么运行就失败了它的唯一任务。

**之后的会话会复用之前某次运行的发现吗？**

不。没有任何东西会自动加载过去的研究文件；它只是一个存在于仓库中的文档，直到人或技能指向它。这很早之前就被提出作为对设计的最强挑战：“价值在于 markdown 变成稍后代理重新读取的上下文，而不是获取本身。一次性写入的死文件只是一种花哨的搜索。”已发布的技能无法解决它。实际上，该文件通过被刻意纳入下一步来赚取它的价值：将其附加到规范上，引用到追问会话中，或者指向一个 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket)。

**为什么不直接让代理去读文档呢？**

你可以这样做，而一个恰好表达了这一点的两行提示词，正是这个技能所取代的做法。相比提示词，技能多买来两样东西：它在后台运行，所以你的会话能保持[上下文](https://www.aihero.dev/ai-coding-dictionary/context)干净；而且主要来源约束和带引用的文件输出每次都以相同方式产出，而不是取决于你碰巧怎么措辞。相对于[工具框架](https://www.aihero.dev/ai-coding-dictionary/harness)自带的深度研究模式，区别在于产物和来源纪律，而不是搜索本身。如果两行提示词就能在小问题上给你所需，那就用两行提示词。

**它什么时候停止阅读？**

该技能没有停止标准，这表现为两个看似相反但其实是同一个缺陷的抱怨：代理钻得太深，以及覆盖了广泛话题却漏掉了那个至关重要的具体细节。一位实践者将其描述为“深度研究技能有时有点太深了。告诉代理去研究通常会导致遗漏关键细节。”范围由你决定。一个狭小、可回答的问题（一个 API、一种行为、一个版本声明）比“研究 X”返回的结果好得多。

**`/wayfinder`创建了研究任务票。我应该自己解决它们吗？**

不，它现在会为你触发它们。自 v1.1 以来的未发布更改中，绘图会话会为每个研究任务票派生一个 `/research` 子代理，并行处理它们，并在一个一次性使用的 `research/<name>` 分支上捕获发现，该分支带有来自任务票的 [context pointer](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。研究任务票是 wayfinder 每会话一个任务规则的唯一例外，因为它们是 [AFK](https://www.aihero.dev/ai-coding-dictionary/afk)：没有任何东西在等你。关于这些分支有两个已知的问题：子代理已被看到从不打算合并的分支打开草稿 PR（[issue #576](https://github.com/mattpocock/skills/issues/576)），而稍后删除分支会破坏任务票持有的上下文指针。

## 如果它起作用了

* 你自己的会话仍在继续。如果你坐在那里看着它读取，说明委派并没有发生。
* 只出现一个新的后台任务。如果出现第二个名称几乎相同的任务，那就是嵌套错误。
* 会新增一个 Markdown 文件，存放在仓库原本用于记笔记的文件夹中，并且代理会告诉你该文件的路径。
* 其中的每项声明都带有链接，随机跟随其中两项会带你到达官方文档、规范或实际的源文件，而不是某人对它的描述。
* 仅凭该文件，你就能做出之前卡住的决定，无需自己回头去查阅原始来源。

## 它在系统中的位置

它是一个随时可拿起的独立工具，用于滋养思考型技能，而不是待在构建链中。它的文件是需要*带入*流程的东西：[grilling](https://aihero.dev/skills-grilling) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 在事实已经摆在桌面上的时候会提出更尖锐的问题，而 [to-spec](https://aihero.dev/skills-to-spec) 可以基于它进行综合。[wayfinder](https://aihero.dev/skills-wayfinder) 是唯一直接调用它的技能，通过 `/research` 子代理解析其地图上的每个研究任务。要查看完整地图，请参阅 [ask-matt](https://aihero.dev/skills-ask-matt)。
