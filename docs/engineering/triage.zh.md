## 功能说明

`triage` 将项目跟踪器上的问题通过一个小型的 **状态机**（由分类角色组成）进行处理——对它们进行分类、验证索赔、如果需要将其整理好，并留下供代理使用的简报。

它不会盲目打标签。每个经过分类的项目都恰好携带一个 **category** 角色（`bug` / `enhancement`）和一个 **state** 角色（`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`），并且它会 *建议并等待* —— 它会告诉您它的分类和状态决定及其理由，然后仅在您的指导下采取行动。在将任何内容提升到 `ready-for-agent` 之前，它会先验证索赔：重现错误，检出 PR 并运行。

## 何时使用

您通过输入 `/triage` 并用自然语言描述您想要的内容来调用它——代理不会自动调用它。"给我看任何需要我关注的东西"，"让我们看看 #42"，"把 #42 移到 ready-for-agent"。

当您的跟踪器中有原始、未经评估的报告，并且您希望对其进行排序、验证并转化为代理或人类可以接手的工作时，请使用它。要将 settled 的对话转化为新的规格说明，请使用 [to-spec](https://aihero.dev/skills-to-spec)；要将现有的规格说明拆分为工单，请使用 [to-tickets](https://aihero.dev/skills-to-tickets)。`triage` 是反向的——它处理 *已经* 落入跟踪器中的内容。

## 前置条件

`triage` 会读取和写入您的跟踪器，因此 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 必须先配置好跟踪器和标签映射。上述角色名称是 **canonical**（规范的）——您的跟踪器中的实际标签字符串可能会有所不同，该映射就是设置所提供的。配置还决定外部 PR 是否算作请求面，以及谁算作外部人员。

## PR 是带有代码的问题

当跟踪器将外部拉取请求视为请求面时，`triage` 会通过 *相同* 的机器运行它们：相同的分类角色、相同的状态、相同的转换——状态只是针对差异进行检查而不是报告。`ready-for-agent` 意味着附带了简报，代理应该在代码上采取下一步；`ready-for-human` 意味着它已准备好合并。发现功能仅显示外部 PR，但明确命名的 PR 无论作者是谁都会被分类。

## 在提供简报前进行验证

将 `triage` 与临时标签区分开来的步骤是验证。它根据报告者的步骤重现错误，或者检出 PR 并运行测试，然后报告结果：通过代码路径确认、失败或细节不足（这本身就是一个强烈的 `needs-info` 信号）。它还运行两次代码库检查——**redundancy**（这已经实现了吗？如果是，那就是 `wontfix`）和 **prior rejection**（`.out-of-scope/` 是否已经说“不”？）。经过确认的验证会生成更强的代理简报；猜测则不会。

## 判断是否生效

* 它接触到的每个项目都以恰好一个分类角色和一个状态角色结束——从未为零，也从未有两个冲突的状态。
* 它会将带有推理的建议交给您并等待，而不是自行重新打标签。
* 在任何内容达到 `ready-for-agent` 之前，会重现错误并运行 PR。
* 它发布到跟踪器的每条评论都以 `> *This was generated by AI during triage.*` 免责声明开头。

## 在系统中的位置

`triage` 是对您的跟踪器进行的 **周期性维护** 扫描——每当报告堆积时运行它，以保持队列有序并使 `ready-for-agent` 列值得信赖。它位于跟踪器的最前端，构建链的上游：它编写的简报是 [tdd](https://aihero.dev/skills-tdd) 稍后用来实现的。当请求需要完善时，它会依赖 [grilling](https://aihero.dev/skills-grilling) 和 [domain-modeling](https://aihero.dev/skills-domain-modeling) 一次一个问题地将其整理好。它的近邻是 [to-spec](https://aihero.dev/skills-to-spec)，后者从新的对话中填充跟踪器，而 `triage` 处理其中已有的内容。当您不确定哪个技能或流程合适时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为您指路。
