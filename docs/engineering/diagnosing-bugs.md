## 它做什么

`diagnosing-bugs` 会对一个棘手的 bug 或性能回归执行六阶段诊断：构建复现、将其最小化、对假设排序、插桩、用回归测试修复、清理。

它不会让 agent 形成理论，直到存在一个**紧密**的反馈循环：一个已命名的命令，已经运行过一次，在这个 bug 上变红，修复时变绿。被赋予 bug 报告的 coding agent 的默认行为是读取代码并猜测；本技能会阻止这种行为。如果没有能变红的命令存在，就没有第二阶段。那个唯一的关卡就是本技能的用途。一旦信号存在，之后的所有工作（二分法、假设测试、插桩）都是机械性的。

## 何时使用它

输入 `/diagnosing-bugs`，或者当任务符合条件时，agent 会自行调用它：它是由模型触发的，并在"diagnose" / "debug this"或报告某物损坏、抛出异常、失败或缓慢时触发。

在棘手的问题上才使用它：一眼看不透的 bug、间歇性的偶发失败、在两个已知良好状态之间悄悄潜入的回归。它设计上就是重量级的，对于你想一条消息就得到回答的问题，它是错误的工具。

| 你的情况                     | 去哪里                                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| 你能将其描述为症状的特定缺陷           | 本技能                                                                                                  |
| 已知前后对比的慢端点或时序回归          | 本技能：它有一个性能分支（建立基线测量，然后二分法）                                                                           |
| "这个代码库中的瓶颈在哪里？"，没有具体症状   | 不是本技能。它诊断一个已知的失败，不做审计                                                                                |
| 来自他人的原始 bug 报告，尚未确认或整理成文 | [triage](https://aihero.dev/skills-triage)优先                                                         |
| 用于回答设计问题的临时代码，而不是追踪缺陷    | [prototype](https://aihero.dev/skills-prototype)                                                     |
| 以测试优先的方式构建计划中的行为         | [tdd](https://aihero.dev/skills-tdd)                                                                 |
| 没有好的接缝来锁定这个 bug          | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)：本技能会直接在此处移交 |

## 紧密循环就是本技能

第一阶段获得了不成比例的投入，因为它是唯一困难的阶段。本技能给出了一组构建循环的方法阶梯，大致按优先顺序排列：

1. 在能触及该 bug 的任何接缝处编写一个失败的测试。
2. 针对正在运行的开发服务器执行 curl 或 HTTP 脚本。
3. 使用固定输入调用 CLI，并与已知正确的快照进行 diff 对比。
4. 无头浏览器脚本，对 DOM、控制台或网络进行断言。
5. 重放捕获：保存的请求、有效载荷或事件日志，在隔离的代码路径中运行。
6. 一次性的测试工具：系统的最小子集，一次函数调用。
7. 针对"输出偶尔出错"的属性测试或模糊测试循环。
8. 一个可以交给 `git bisect run` 的二分查找工具。
9. 差异化循环：相同的输入，旧版本与新版本对比。
10. 一个[人在回路](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash 脚本，作为最后手段。本技能为此附带了一个 `scripts/hitl-loop.template.sh`：agent 运行该脚本，你在终端中跟着提示操作，你的回答会以可解析的输出返回。

*一个*循环不是目标。**紧密**才是：快速（秒级）、确定性（每次运行结果一致）、精准（断言你具体的症状，而不是"没崩溃"），且 agent 可无人值守运行。30 秒的不可靠循环几乎比没有好不到哪里去。对于只在某些时候出现的 bug，目标不是干净的复现，而是**更高的复现率**：循环触发器，并行化，增加压力，注入睡眠，直到不可靠率足够高以便进行调试。

当它确实无法构建出这样的循环时，指令要求它停下来并说明情况，列出它尝试过的方法，并向你请求[环境](https://www.aihero.dev/ai-coding-dictionary/environment)访问权限、一份捕获到的产物，或添加临时插桩的许可。它无论如何都不应继续推进假设。

## 阶段之间的关卡

各个阶段就是关卡，而不是检查清单。每个关卡都会拒绝打开，直到某个具体条件成立。

| 关卡     | 必须满足的条件                                                                 |
| ------ | ----------------------------------------------------------------------- |
| 进入第二阶段 | 一条已命名的命令，已经运行过并连同其输出一起粘贴出来，且能在这个 bug 上变红                                |
| 进入第三阶段 | 复现已成功 *和&#x20;*&#x20;minimised: every remaining element is load-bearing |
| 进入第四阶段 | 存在 3–5 个已排序的、可证伪的假设，每个假设都说明其预测，并且在测试任何一个之前展示给你                          |
| 进入第五阶段 | 探针映射到具体的预测，一次只改变一个变量，每条调试日志都打上 `[DEBUG-a4f2]`风格的标签，这样清理时只需一次 grep       |
| 完成     | 原始复现不再出现，插桩已清除，而且被证明正确的假设已写入提交信息                                        |

第五阶段有一个值得了解的逃生舱。回归测试是在修复之前编写的，但仅当存在一个**正确的接缝**时：即测试在调用点执行时能处理实际 bug 模式的地方。如果唯一的可用接缝太浅，技能被告知要说明这一点，而不是编写一个给予虚假信心的测试。这种缺失本身就是一个发现，它将事后分析路由到 `improve-codebase-architecture`。

## 常见问题

**它在快速问题上触发，而我只想要一个直接答案。**
这是该技能报告最多的问题，而且确实存在。特别是在 GPT-5.6-Sol 上，用户报告它会在对问题的简单描述上触发："模型反而触发了相当正式的 diagnosing-bugs 技能。它随后会去构建一个复现场景（通常构建一个价值有限的模拟场景），然后才给我回复或建议。这导致了相当长的回复延迟。" 四个不同的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了相同的情况。接受的修复方法是先使用较轻的方法，仅在问题值得时才升级到较重的方法，但该更改尚未落地。该技能是根据 Claude Code 的调用行为校准的；一个[模型](https://www.aihero.dev/ai-coding-dictionary/model)如果激活阈值较低，就会过度触发它。在它被升级之前，实用的修复方法是说出你想要的（"只回答这个，不要诊断"）或者在你的[harness](https://www.aihero.dev/ai-coding-dictionary/harness)中禁用对其的模型调用。

**我可以把它指向一个代码库并询问性能问题在哪里吗？**
不能。它诊断一个你已经可以命名的失败。它的性能分支用于有症状的回归（建立基线测量，然后二分法，先测量后修复），而不是用于主动扫描。主动版本的技能已被[提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有相关的技能。

**它会在写修复之前停下来问我吗？**
不。只有第三阶段有人类检查点：任何假设被测试之前，都会向你展示排序后的假设列表，如果你不在场，它会根据自己排序继续。插桩和修复之间没有关卡，所以 agent 可能在你同意其根本原因之前就开始编写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 请求设置这个关卡，目前仍是开放的。如果你想要它，请在调用技能时说明。

**我已经对这个 bug 报告运行了 `/triage`。这是重复工作吗？**
部分是，而且两个技能都不承认这一点。正如一位读者所说："Triage 的第 3 步本质上是对 diagnosing-bugs 第 1-2 阶段的浅层、有界实例，但两个文件都没有提到对方。" Triage 做一个有界的"这实际上是个 bug 吗，以及表面是什么"的检查；本技能做的是彻底的版本。先运行 triage 不会浪费（它的验证通常给了你第 1 阶段的大部分原始材料），但在这里要预期会正确地重做它，并且预期不会有交叉引用告诉你这一点。

**它粘贴的复现输出会泄露机密吗？**
可能会。技能要求 agent 粘贴调用及其输出，并请求 HAR 文件、日志转储和核心转储等产物。没有任何一项是通过指令进行清洗的。[Issue #674](https://github.com/mattpocock/skills/issues/674) 正好提出了这个问题（凭据、令牌、cookie 和个人数据随同进入聊天、issue 或 PR），并提出了编辑护栏。它是开放的且未实现。目前将编辑作为你的工作来处理，特别是在输出进入任何公共领域之前。

**我的安全扫描器将此技能标记为高风险。** Snyk 标记了它，但这是一个误报。它是该技能集中唯一一个随附可执行 shell 脚本（`hitl-loop.template.sh`）以及运行说明和 curl 开发服务器说明的技能。随附的 `.sh` 文件加上运行说明再加上出站 HTTP，足以触发静态扫描器。该脚本本身只有约 30 行用于暂停等待人工输入的 `read -r -p` 提示。扫描器评估的是能力面，而不是已证实的漏洞。

**`/diagnose` 发生什么了？**
在 v1.0.0 中重命名为 `/diagnosing-bugs`。旧名称不再存在。任何链接到 `/diagnose`（包装技能、保存的提示）的东西都需要更新。

## 如果它起作用了

* 它会在给出任何理论之前先向你展示一条命令及其红色输出。如果理论先出现，说明该技能没有在运行。
* 它复现的失败是你报告的那个，而不是它在途中发现的类似失败。
* 它在开始猜测之前会先缩小复现范围，并能告诉你为什么剩下的每一部分都不可或缺。
* 在测试任何假设之前，你会看到一个按优先级排序的 3–5 个假设列表，每个假设都带有你能证伪的预测。
* 它添加的每条调试日志都带有类似 `[DEBUG-a4f2]` 的标签，而当它宣布完成时，grep 该标签应该返回空结果。
* 提交或 PR 消息会标明哪个假设是正确的。
* 当它无法用测试锁定这个 bug 时，它会直说，而不是写一个浅层测试。

## 它在系统中的位置

`diagnosing-bugs` 是一个随时可用的独立技能。当有东西坏了你就进入它，当修复及其回归测试完成后你就退出；它不保存状态，也不需要任何前置设置。[ask-matt](https://aihero.dev/skills-ask-matt) 会把“有东西坏了”的请求路由到这里。

两个邻居很重要。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真正的发现是代码没有接缝来锁定 bug 时接管[移交](https://www.aihero.dev/ai-coding-dictionary/handoff)；建议是在修复完成后做出的，那时有更多信息。[triage](https://aihero.dev/skills-triage) 坐落在它上游，用于来自其他人的原始报告形式的 bug，并做前两个阶段的浅层版本。
